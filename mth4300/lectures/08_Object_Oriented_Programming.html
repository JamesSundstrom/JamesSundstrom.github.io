Lecture 08: Object-Oriented Programming

We're finally ready to start defining our own classes. As in Python, a class bundles together data and the methods that work with that data, as well as controlling who can access the data. As you might expect by now, C++ expects us to be a bit more hands-on with the details of how our classes work.

Encapsulation

One of the purposes of a class is to enforce encapsulation: we bundle data together with the methods not only for convenience, but also because that allows us to restrict access to the object's underlying data. Someone who wants to modify the object's internal data can only access the data through the provided methods, so that the data can only be modified in ways intended by the creator of the class. As a simple example, suppose we have a class Counter representing a counter that should only ever go up by 1; maybe it has an attribute n representing the value of the counter. Without encapsulation, a programmer could accidentally (or maliciously) modify the value of the counter in unintended ways by writing something like c.n -= 10. With proper encapsulation, code that uses Counter doesn't have access to the attribute n directly; instead, the Counter class might make available an increment() method that adds 1 to n. This enforces the original designer's intention that the only way to modify n should be by adding 1.

Similarly, if you're writing a class that represents a bank account, you might not want to allow the balance to become negative. If the balance attribute were publicly available, people could write code like acct.balance -= 1000, which might make the balance negative. Instead, you could make balance a private attribute and provide a withdraw method that handles withdrawals however you want. In particular, if the bank later changes its policy and decides to start letting (some or all) customers overdraw their accounts, you need only update the withdraw method to implement that new policy; if outside code implemented withdrawals by modifying the balance directly, you would need to find and update every such piece of code.

A related benefit of encapsulation is that it allows us to change the implementation later. If we write code that accesses the attributes of a class directly, then we won't be able to change those attributes later without breaking the existing code. For example, what if we have data stored in one way, but we later realize that there was a more efficient way to store it? If there's already a lot of code that assumes the data will be stored in the original way, we're stuck with it. If instead the existing code only accesses the data through methods, then we can always change the internal storage of the class, and we need only update those methods to access the data in the new way.

There are three basic levels of privacy that you might want:

  • public: The attribute can be accessed by anyone.
  • protected: the attribute can only be accessed by the class or its subclasses.
  • private: The attribute can only be accessed within the class itself.

This idea existed in Python, but not strictly enforced by the language. Instead, Python uses the convention that an attribute name beginning with a single underscore is protected: the language doesn't prevent programmers from accessing the attribute directly, but the naming convention serves as a warning that you're using the class incorrectly. An attribute that begins with a double underscore is private. Python makes it more difficult to access a private attribute outside the class through name mangling: modifying the name of the attribute to make it harder to access accidentally. Nonetheless, such attributes can still be accessed if you try. Part of the design philosophy of Python is "We're all consenting adults here," meaning that if you really want to do something as a Python developer, the language will let you do it. C++ adopts the opposite philosophy: if an attribute is marked as private, it cannot be accessed outside the class.

Structs and Classes

We've seen structs previously: in our lesson on pointers, we defined an Employee structure: 

#include <iostream>

struct Employee {
    std::string name;
    Employee* supervisor;
};

int main() {
    Employee DavidWallace{"David Wallace", nullptr};
    std::cout << DavidWallace.name << std::endl;
    return 0;
}

It turns out that we could have done almost the exact same thing with a class: 

#include <iostream>

class Employee {
    std::string name;
    Employee* supervisor;
};

int main() {
    Employee DavidWallace{"David Wallace", nullptr};
    std::cout << DavidWallace.name << std::endl;
    return 0;
}

But this code doesn't compile! The reason is that members of a struct are public by default, whereas members of a class are private by default. Therefore the code in main that attempts to access name is illegal.

In fact, the default access level is the only technical difference between struct and class; they are otherwise completely interchangeable. In practice, struct is generally used for pure data bundles with no methods, while class is used to encapsulate data and methods.

Of course, we can override the default access levels if we want: 

#include <iostream>

class Employee {
public:
    std::string name;
    Employee* supervisor;
};

int main() {
    Employee DavidWallace{"David Wallace", nullptr};
    std::cout << DavidWallace.name << std::endl;
    return 0;
}

Note that public: is not indented, but the attributes being defined are. (As usual, the whitespace doesn't matter technically, but following the standard formatting makes your code easier to read.)

Managing access

Let's try to write the simple Counter class that we mentioned earlier. This class will have one member variable count_ and two member functions getValue and increment. 

#include <iostream>

class Counter {
public:
    int getValue() const { return count_; }
    void increment() { ++count_; }
private:
    int count_{0};
};

int main() {
    Counter c;
    std::cout << c.getValue() << std::endl; // 0
    c.increment();
    c.increment();
    std::cout << c.getValue() << std::endl; // 2
    // std::cout << c.count_ << std::endl; // Not allowed
    return 0;
}

There are several interesting things to note about this code:

  • The private member variable count_ has a name which ends in a single underscore. This is a common C++ convention to indicate that something is a private member variable.
  • Note that count_ is initialized to 0 when a new Counter object is created.
  • Since the variable that stores the count is private, the class must now provide methods that allow the user to access it in the intended ways: increment the count, or view the value of the counter.
  • Note the semicolon after the class declaration: this is mandatory.
  • In main(), the code Counter c; tells the compiler to create an object of type Counter. You might wonder how this is possible, since we haven't written code to tell the compiler how to do that. (In Python, we would have the __init__ method.) If you don't define any constructor, the compiler will automatically generate a default constructor for you. The code Counter c; implicitly calls this constructor to create a new Counter. We'll see later how you could define your own constructor.
  • The const on the declaration of getValue tells the compiler that the getValue method doesn't alter any of the attributes of its object. If you want to be able to call a method with a const object, the method needs to be declared const to tell the compiler that's safe. (Of course, a const Counter wouldn't make much sense, since it wouldn't be able to count, but you might want a const reference to a non-const Counter.) The below example illustrates what goes wrong without the const: 
#include <iostream>

class Counter {
public:
    int getValue() { return count_; }
    void increment() { ++count_; }
private:
    int count_{0};
};

int main() {
    Counter c;
    const Counter& r = c;
    c.increment();
    std::cout << r.getValue() << std::endl; // Not legal!
    return 0;
}

Of course, if you put the const back on the declaration of getValue, the above code works.

As a rule, you should always put const on any method that doesn't modify the object. This takes basically no effort. In return, it prevents you from accidentally modifying the object when you didn't mean to, and it allows you to use the methods with const objects.

In the preceding examples, we wrote all the code for the class methods directly inside the class declaration. In this case, the methods were very brief, so this was fine. But you can imagine that this might make our code difficult to read if the methods had long, complicated code. If you're trying to understand how to use a class, it would be nice to be able to see exactly what attributes/methods are declared without needing to wade through the code for each method to find the next one. C++ lets us move the definitions of the class methods outside the class declaration. (There are also technical reasons besides readability why you might want to do that, but we won't worry about that for now.) 

#include <iostream>

class Counter {
public:
    int getValue() const;
    void increment();
private:
    int count_{0};
};

int Counter::getValue() const { return count_; }
void Counter::increment() { ++count_; }

int main() {
    Counter c;
    c.increment();
    std::cout << c.getValue() << std::endl; // 1
    return 0;
}

Note that when we define the class methods outside the class, we use the scope resolution operator :: to tell the compiler tha tthis is Counter's getValue method, not a separate function named getValue.

Note also that inside the Counter class declaration, we need a semicolon after each method that's declared but not defined.

Constructors

A constructor is the function that runs automatically when an object is created. It has the same name as the class, and no return type. For example, we can add an explicit constructor to our Counter class rather than relying on the compiler to create one for us. We can even add multiple constructors, so that new objects can be created in different ways. 

#include <iostream>

class Counter {
public:
    Counter(); 
    Counter(int start);
    int getValue() const;
    void increment();
private:
    int count_;
};

Counter::Counter() : count_(0) {}
Counter::Counter(int start) : count_(start) {}
int Counter::getValue() const { return count_; }
void Counter::increment() { ++count_; }

int main() {
    Counter c;
    c.increment();
    Counter d(5);
    d.increment();
    std::cout << c.getValue() << ' ' << d.getValue() << std::endl; // 1 6
    return 0;
}

As you probably expected, Counter c calls the default constructor (which creates a counter starting from 0), while Counter d(5) calls the parametrized constructor that accepts an int parameter telling the counter where to count from.

Notice the count_(0) before the (empty) body of the constructor. This is a member initializer list, which initializes class members before running the code in the constructor body. It is generally preferred to initialize class members this way, when possible. (Of course, you're allowed to mix the two -- have a member initializer list and also write code in the body.) One possible source of confusion is that class members are always initialized in the order they're declared, regardless of the order of the member initializer list. If some members are defined in terms of others, this could cause a bug if they're not initiallized in the order you're expecting. To avoid this issue, the member initializer list should always be written in the same order that the members are declared: 

#include <iostream>

class Pair {
public:
    Pair(int n) : y_(n), x_(y_+1) {} // Error, because it tries to initialize x_ before y_
    int x_;
    int y_;
};


int main() {
    Pair p(5);
    std::cout << p.x_ << ' ' << p.y_ << std::endl;
    return 0;
}

The above code may compile (depending on your compiler settings), but if it does, it will probably print "1 5" instead of the "6 5" you might expect. This is because x_ is initialized to y_+1 before y_ is initialized, so it probably used the default value 0 for y_.

Another possible pitfall: if you define any constructor, the compiler no longer creates a default constructor for you, so you will need to define one yourself if you still want a default constructor. For example, the following code would not work: 

#include <iostream>

class Counter {
public:
    Counter(int start);
    int getValue() const;
    void increment();
private:
    int count_{0};
};

Counter::Counter(int start) : count_(start) {}
int Counter::getValue() const { return count_; }
void Counter::increment() { ++count_; }

int main() {
    Counter c; // Illegal! There's no default constructor anymore.
    std::cout << c.getValue() << std::endl;
    return 0;
}

Destructors

A destructor is a method that runs automatically when your object is deleted (either explicitly, or because it goes out of scope). The destructor should release any heap resources that the object owned. As such, a class with no heap resources usually does not need an explicit destructor, because nothing needs to be destroyed. (Technically, a destructor is still called when the object is deleted; it's just that the compiler provides a default destructor that does nothing.)

Strictly speaking, there's no requirement that the destructor can only free heap resources. You can tell it to do anything that you want done every time an object is destroyed. For example, you can ask it to print a message, which can sometimes be helpful for debugging (or occasionally even a feature in your finished program).

The destructor is defined with the exact same syntax as the constructor, except that it's prefixed with a tilde (~). To demonstrate the destructor, let's start creating a Polynomial class. We'll need to store the coefficients of the polynomial. In the real world, it would probably make sense to use a std::vector to store them, but we'll use a C-style array so that we have heap memory that we can demonstrate deleting. 

#include <iostream>
#include <vector>
#include <numeric>

class Polynomial {
public:
    Polynomial(const std::vector<int> &coefficients);
    ~Polynomial();
    int eval(int n) const;
private:
    int* coefficients_;
    int degree_;
};

// Copy the given coefficients vector into coefficients_, while also removing 
// any leading zeros so that degree_ is calculated correctly.
Polynomial::Polynomial(const std::vector<int> &coefficients) {
    int i;
    for (i=0; i < coefficients.size(); ++i) {
        if (coefficients[i] != 0) {
            break;
        }
    }
    degree_ = coefficients.size() - i - 1;
    coefficients_ = new int[degree_ + 1];
    for (int j = i; j < coefficients.size(); ++j) {
        coefficients_[j-i] = coefficients[j];
    }
}

Polynomial::~Polynomial() {
    delete[] coefficients_;
}

int Polynomial::eval(int n) const {
    auto f = [n](int acc, int val) { return acc * n + val; };
    return std::accumulate(coefficients_, coefficients_ + degree_ + 1, 0, f);
}

int main() {
    Polynomial f{{3, -2, 5}}; // Initialize f(x) = 3x^2 - 2x + 5
    std::cout << f.eval(10) << std::endl; // 285
    return 0;
}

Make sure you understand the above code; we're going to continue using Polynomial for more examples later.

Basically, the constructor just copies the given coefficients into our array coefficients_. However, this is complicated by the fact that we don't want to include leading 0's in our coefficient array; if we receive the array {0, 0, 2, 1}, we want to store the polynomial as 2x + 1, not 0x3 + 0x2 + 2x + 1.

The destructor is quite simple, because it only needs to free the memory for the array. (As mentioned earlier, if we had stored the coefficients in a std::vector<int>, we wouldn't need to write an explicit destructor at all.) Later, we'll see examples where the destructor is more difficult to write.

Finally, we have an eval() method, which evaluates the polynomial at a given point. The example code defines f to be the polynomial 3x2 - 2x + 5, and then evaluates it at x=10, which gives 285.

The this pointer

When you are writing code for a method within a class, sometimes you need to refer to the object that the method was called on. You can do that using this, which is a pointer to the object. This can be useful if you want to pass the object as an argument to another function, or for a method to return the object itself. It can also be useful when a member variable's name is shadowed by another variable with the same name; in that case, the member variable can be accessed via this, as in the below example. 

#include <iostream>
#include <string>

class Line {
public:
    Line(double a, double b, double c, double d);
    std::string toString();
    double m;
    double b;
};

// Constructs the line through (a, b) and (c, d)
// Note that the class member b is shadowed by the stupid argument name b
Line::Line(double a, double b, double c, double d) {
    m = (d - b) / (c - a);
    this->b = b - a * m; // We can access the class member b as this->b
}

// Very crude way of representing a line as a string.
std::string Line::toString() {
    return "y = " + std::to_string(m) + "x + " + std::to_string(b);
}

int main() {
    Line line(1, 3, 3, 7); // y = 2x+1 goes through (1, 3) and (2, 7)
    std::cout << line.toString() << std::endl;
    return 0;
}

Of course, shadowing a variable that you need is pretty stupid, so a better solution would be to choose better variable names in the first place. (For example, Line::Line(double x0, double y0, double x1, double y1) would solve our shadowing problem and make the code easier to understand.) But sometimes it might be necessary -- maybe somebody else made this mess, and you want to get their code working before you start trying to clean it up by renaming variables.

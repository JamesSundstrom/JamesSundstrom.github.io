Lecture 05: Memory and Pointers

Unlike Python, C++ sometimes requires you to think about the specifics of how data is stored in the program's memory.

Memory

A C++ program has two different sections of its memory, the stack and the heap, which serve different purposes and need to be handled in different ways. It's important to understand the differences between them.

The stack

The stack is where local variables (variables that live inside a function, such as main()) exist. The compiler knows what variables are needed and how much memory is needed to store each one, so it knows exactly how much space to allocate on the stack. When a function is finished running, its local variables are no longer needed, and they can be removed from the stack.

Indeed, that property explains why this section of memory is called the stack. In computer science, a stack is a last-in-first-out (LIFO) data structure, meaning that the last data put onto the stack is the first data removed. This is just like a real stack: if you make a stack of boxes in the real world, and then want to read its data, you had better remove the top (last-added) box first.

A LIFO order is exactly what we want when we're calling functions. Suppose your code calls a function f, which calls a function g, which calls a function h. When f gets called, its local variables are put on the stack. (The allocated memory for f is called its stack frame,) Then f calls g, so the stack frame for g is added to the stack. Then g calls h, so the stack frame for h is added to the stack. Finally, h finishes running, so its stack frame can be removed from the top of the stack, freeing that memory in case it's needed later by some other function. This returns control to g, which can finish running and remove its stack frame. Then this returns control to f, which can finish running and remove its stack frame. Note that this is LIFO, as promised: the last function called (h) was the first to have its stack frame removed.

Each variable has an address that tells the computer the exact memory location where it can be found. By convention, this address is given in hexadecimal (base 16, where 'a' is the digit 10, 'b' is the digit 11, and so on). C++ lets you, the programmer, access this memory address using the address-of operator &. If you place the & before a variable, C++ gives you the address of that variable. (Perhaps appropriately, this looks a lot like the syntax used to declare a reference.)

Naturally, it doesn't make any sense to take the address of something that doesn't have a permanent address, e.g., trying to take the address of a literal value in your code is an error: 

#include <iostream>

int main() {
    std::cout << &42;
    return 0;
}

Here's an example using the address-of operator properly: 

#include <iostream>

int main() {
    int x{5}, y{-6};
    long long z{3};
    int w{42};
    std::cout << &x << '\n' << &y << '\n' << &z << '\n' << &w << std::endl;
    return 0;
}

I just ran this code, and it printed the following:

0x91c13ff6ac
0x91c13ff6a8
0x91c13ff6a0
0x91c13ff69c

If you run the code yourself, you will (almost certainly) get different output, but following a similar pattern. In fact, you will almost certainly get different output every time you run this program, even if you run it repeatedly on the same computer. This is because the program is not assigned the same section of your computer's memory every time it runs, so naturally the variables will have different addresses each time.

The "0x" at the beginning of each address is a standard convention in computer science which indicates that the number is in hexadecimal. Then the number gives the address of the byte where the variable starts. (As mentioned previously, bytes are the smallest addressable units of memory, so we don't get an address for an individual bit.) In the above example, the variable x starts at the address 0x91c13ff6ac. With my compiler (as with almost all modern C++ compilers), an int occupies four bytes, so this means that x is stored in bytes 0x91c13ff6ac, 0x91c13ff6ad, 0x91c13ff6ae, and 0x91c13ff6af.

After declaring x, we next declared y. Since y is also an int, it also needed 4 bytes of memory, so it started at 0x91c13ff6a8, which is 0x91c13ff6ac - 4; this leaves it exactly the 4 bytes that it needs (0x91c13ff6a8, 0x91c13ff6a9, 0x91c13ff6aa, and 0x91c13ff6ab), so no space is wasted. (For technical reasons, the compiler will sometimes optimize by leaving a little space, but that's not important to us.)

After that, z is a long long, so it needs 8 bytes: 0x91c13ff6a8 - 8 = 0x91c13ff6a0, so z starts at address 0x91c13ff6a0. Finally, w needs 4 bytes, and 0x91c13ff6a0 - 4 = 0x91c13ff69c, so that's the address of w.

The heap

The other section of memory available to a C++ program is called the heap. When possible, we prefer to use the stack, because it is faster to use and generally safer (for reasons we'll discuss later). However, sometimes you need to use the heap.

For example, you may need to use the heap if you're creating an object that you want to outlive the function that created it. Remember that any variables allocated by a function on the stack are removed once the function goes out of scope. If your function is supposed to create and return a new object, it would be silly for that object to be erased when the function returns. We haven't had to worry about this yet, but we'll need to worry about that later, such as when we start defining our own classes.

Pointers

A pointer is a variable that stores the address of some data. In some ways, it's similar to a reference. But in other ways, it's very different, and understanding the difference is crucial. One difference is that the pointer is actually its own box in memory. It's not just another name that we can use to refer to an existing memory address; when we declare a pointer, we're setting aside a new piece of memory, which will store the address of another object.

The declaration for a pointer looks very similar to the declaration for a reference, except that we use * instead of &. However, the initialization is different; we initialized a reference to an int by putting the name of the int on the right-hand side. The declaration and initialization of the reference don't take up any additional memory; they only tell the compiler to recognize a new name for an existing block of memory. With a pointer, the declaration sets aside a new piece of memory to store an address, and then the initialization needs to provide the address that will be stored there. Therefore the right-hand side of the assignment needs to be an address, which we can get using the address-of operator &: 

#include <iostream>

int main() {
    int x = 42;
    int* p = &x;
    std::cout << p << std::endl; // Prints the address of x (0x...)
    return 0;
}

There are two blocks of memory in play here: the block of memory set aside for p, which is being used to store an address, and the block of memory set aside for x, which is the memory whose address is stored in p. When we print p, it acts just like any other non-reference variable: it prints the contents of p's memory, i.e., an address. But what if that wasn't the behavior you wanted? What if we wanted to use p to access the value stored in x? For that, we use the dereference operator *: 

#include <iostream>

int main() {
    int x = 42;
    int* p = &x;
    std::cout << *p << std::endl; // Prints 42
    return 0;
}

Note that we can use *p on the left or right side of an assignment. In the below code, y = *p, copies the value stored in *p (i.e., the value of x) into y, and then *p = 5 copies the value 5 into the memory pointed to by p, which is the memory used by x, just like when we assign to a reference: 

#include <iostream>

int main() {
    int x = 2, y = 3;
    int* p = &x;
    y = *p;
    *p = 5;
    std::cout << *p << ' ' << x << ' ' << y << std::endl; // Prints 5 5 2
    return 0;
}

Unlike a reference, the value of a pointer can be reassigned after it is declared. (As a result, it is legal to declare a pointer without initializing it, since it can be given a value later.) Try to predict what the following code will print before you run it: 

#include <iostream>

int main() {
    int x = 2, y = 3;
    int* p = &x;
    *p = 5;
    p = &y;
    *p = 7;
    std::cout << *p << ' ' << x << ' ' << y << std::endl;
    return 0;
}

The arrow operator

What if you have a pointer to an object, and you want to access a class member for that object? For example, suppose you have a pointer to a std::string s and you want to access s.size(). You could simply dereference the pointer to get s, and then use the .size() notation directly: 

#include <iostream>

int main() {
    std::string s{"Hello, world!"};
    std::string* p = &s;
    int n = (*p).size();
    std::cout << n << std::endl; // Prints 13
    return 0;
}

However, you have to be very careful with the order of operations. Notice that we wrote (*p).size() above; if we had written *p.size() without the parentheses, C++ would interpret the order of operations as *(p.size()), which is nonsense, and the code would not compile: 

#include <iostream>

int main() {
    std::string s{"Hello, world!"};
    std::string* p = &s;
    int n = *p.size();
    std::cout << n << std::endl; // Prints 13
    return 0;
}

This is mildly annoying. When we do it right, our code is muddied with ugly parentheses, and we need to remember to write those parentheses every time. Fortunately, C++ provides a nicer solution: the arrow operator ->. Applying the arrow operator to a pointer is exactly the same as applying the dot member access operator to the object it points to: 

#include <iostream>

int main() {
    std::string s{"Hello, world!"};
    std::string* p = &s;
    int n = p->size();
    std::cout << n << std::endl; // Prints 13
    return 0;
}

nullptr

C++ has a keyword nullptr which represents the null pointer, a pointer which doesn't point to anything. This serves two main purposes. First, if you wish to declare a pointer without initializing it, you can initialize it to nullptr. That way, if you accidentally dereference it, you don't need to worry that you're dereferencing an uninitialized value (which could lead to undefined behavior). Dereferencing an uninitialized value might treat whatever data is in the uninitialized memory as an address and dereference that random address, or might crash the program immediately, depending on your compiler. (When I run the following code on my computer, it crashes, but when I run it online, it prints a random garbage value.) 

#include <iostream>

int main() {
    int* p;
    std::cout << *p << std::endl; // May crash or print a garbage value
    return 0;
}

Instead of leaving the pointer uninitialized, we could have set it to nullptr instead. Technically, dereferencing nullptr is still undefined behavior according to the C++ standard, but the compiler is more likely to crash when dereferencing a null pointer than it is when dereferencing an uninitialized pointer, which will make the bug easier to diagnose. 

#include <iostream>

int main() {
    int* p = nullptr;
    std::cout << *p << std::endl; // Almost certainly crashes
    return 0;
}

Remember, you should never dereference a null pointer -- but if you're going to dereference a pointer that doesn't point to valid memory, it's probably better for it to be a null pointer than an uninitialized pointer.

The other benefit of nullptr is even more important, because it can be useful in working code, not just for debugging bad code. Sometimes you're not sure whether you will have data for a particular variable. It may be possible to use an obvious garbage value to indicate missing data, e.g., an inventory of -1 might mean that you haven't counted that item yet. But in other cases, there might not be an obvious garbage value. For example, suppose you want to create an Employee structure (struct), where each Employee has a supervisor. (We haven't covered structures yet, so don't worry about the details of how they work. You should be able to tell what's going on well enough to get the idea of the example.) 

struct Employee {
    std::string name;
    Employee supervisor;
};

This code defines a structure where each Employee has a name and a supervisor. But there are two obvious problems with it (and one less obvious, but even more serious, problem). First, there's a real-world problem. Not everybody has a supervisor; we won't be able to represent the CEO by an Employee object. Second, there's a technical problem. We can't create a new Employee without having an existing Employee to serve as the supervisor. So how do we create the first Employee? In fact, we won't even get to the point of that being an issue, because the compiler won't allow us to define a structure like this at all. The problem is that, in order to create an object of type Employee, the compiler would need to know how much memory is needed to store an Employee. But that would require it to store the employee's supervisor, which is also an Employee, so the compiler can't figure out how much memory to set aside for an Employee unless it already knows how much memory to set aside for an Employee. If we continued down this rabbit hole, we would need to set aside memory for the supervisor, and then the supervisor's supervisor, and that person's supervisor, and so on, until the program memory overflowed from too many supervisors.

You might be tempted to try to solve this problem by creating separate SupervisedEmployee and UnsupervisedEmployee classes. You can freely create UnsupervisedEmployee objects whenever you want, and then you can create a SupervisedEmployee using an UnsupervisedEmployee as its supervisor. But this is messy for several reasons. If a supervised employee gets promoted to an unsupervised role, we need to completely change the object representing that employee, not just change data stored within the object. Also, we assumed that a SupervisedEmployee will be supervised by an UnsupervisedEmployee, but that might not be the case in the real world. Often supervisors have their own supervisors that they answer to. Are you going to try to modify the SupervisedEmployee structure to use some kind of polymorphism, so that it can be supervised by either type of employee?

The simple-sounding problem of "Not everyone has a supervisor" is quickly spiraling out of control. Fortunately, C++ provides a better solution. Instead of having an Employee store a copy of its supervisor, instead store a pointer to the supervisor. If an Employee doesn't have a supervisor, we can store nullptr to denote that situation. This avoids the problems that we had before, and it's fairly intuitive for programmers to work with: if an Employee has no supervisor, then the pointer to the supervisor is literally a pointer to nothing, indicating that there is no supervisor.

This probably feels familiar to you from Python. Python has the None object, of type NoneType, that can serve a similar purpose. But we can't do that in C++ because C++ variables need to have definition types; we can't tell the compiler that supervisor is sometimes an object of type Employee and sometimes an object of type NoneType. (That's not 100% true, but it takes more effort to set up a situation like that in C++.) Now we can define Employees with no trouble: 

#include <iostream>

struct Employee {
    std::string name;
    Employee* supervisor;
};

int main() {
    Employee DavidWallace{"David Wallace", nullptr};
    Employee MichaelScott{"Michael Scott", &DavidWallace};
    Employee DwightSchrute{"Dwight Schrute", &MichaelScott};

    std::cout << DavidWallace.name << std::endl;
    std::cout << MichaelScott.name << " reports to " << MichaelScott.supervisor->name << std::endl;
    std::cout << DwightSchrute.name << " reports to " << DwightSchrute.supervisor->name << std::endl;
    return 0;
}

This definition works fine in the real world, because we can easily create employees with or without supervisors. Furthermore, the compiler doesn't object to this definition, because it knows exactly how much memory to set aside when a new Employee is created: memory to store one string and one pointer. The compiler doesn't need to know in advance how much memory is used to store the supervisor because it's not storing the supervisor, only a pointer which contains the address of the supervisor. (Of course, pointers are always the same size because they're simply addresses, regardless of how much memory is used by the thing they point to.)

What if we want to know whether a particular employee has a supervisor? In other words, we want to check whether the Employee object's supervisor pointer is a null pointer or not. We can check that in exactly the way you expect: 

#include <iostream>

struct Employee {
    std::string name;
    Employee* supervisor;
};

bool hasSupervisor(const Employee& e) {
    return e.supervisor != nullptr;
}

int main() {
    Employee DavidWallace{"David Wallace", nullptr};
    Employee MichaelScott{"Michael Scott", &DavidWallace};
    Employee DwightSchrute{"Dwight Schrute", &MichaelScott};

    std::cout << std::boolalpha;
    std::cout << DavidWallace.name << ": " << hasSupervisor(DavidWallace) << std::endl;
    std::cout << MichaelScott.name << ": " << hasSupervisor(MichaelScott) << std::endl;
    std::cout << DwightSchrute.name << ": " << hasSupervisor(DwightSchrute) << std::endl;
    return 0;
}

For more concise code, you can use a pointer directly in a place where a bool is expected. The null pointer is treated as false, and any other pointer is treated as true: 

#include <iostream>

struct Employee {
    std::string name;
    Employee* supervisor;
};

void printSupervisedStatus(const Employee& e) {
    if (e.supervisor) {
        std::cout << e.name << " has a supervisor." << std::endl;
    } else {
        std::cout << e.name << " does not have a supervisor." << std::endl;
    }
}

int main() {
    Employee DavidWallace{"David Wallace", nullptr};
    Employee MichaelScott{"Michael Scott", &DavidWallace};
    Employee DwightSchrute{"Dwight Schrute", &MichaelScott};

    printSupervisedStatus(DavidWallace);
    printSupervisedStatus(MichaelScott);
    printSupervisedStatus(DwightSchrute);
    return 0;
}

const pointers

What does it mean for a pointer to be declared const? There are two possible interpretations:

  • It means that the pointer cannot be used to modify the memory it points to (similar to a const reference.)
  • It means that the pointer itself cannot be modified (i.e., it always contains the same address, but it can be used to modify the value stored at that address).

These are both reasonable things to want, so C++ lets us do both. If we declare const int* p = &x, then p is a pointer to const: it cannot be used to change the value of x (but x can still be changed directly, assuming it wasn't also const). If we declare int* const p = &x, then p is a const pointer: the memory address that it stores cannot be changed, but p can be used to change the value stored at that address.

We can even declare const int* const p = &x if we want both guarantees: the address stored in p can't change, and p can't be used to change the value of x.

As with references, we can't use a non-const pointer to cheat and modify a const object. If x is declared as a const int, then any pointer to x has to be declared as const int*. However, the other way is fine: we can declare a const int* which points to a plain int; as with references, this means that the pointer won't be used to modify the value it points to, even if the value could be modified directly: 

#include <iostream>

int main() {
    int x{1};
    const int y{2};
    const int* p = &x; // Allowed
    int* q = &y;       // Not allowed
    *p = 3;            // Not allowed
    return 0;
}

Pointers and References

You cannot create a pointer to a reference, because a reference is not an object; it is an alias for a memory location, but it does not have its own memory location. Thus int&* p = &r; is illegal. However, you can use the address-of operator on a reference: as you might expect, it returns the address that the reference refers to. As such, if r is a reference to an int x, then int* p = &r; is perfectly legal. For example, the below code is fine: 

#include <iostream>

int main() {
    int x{1};
    int& r = x;
    int* p = &r;
    *p = 5;
    std::cout << x << std::endl; // Can you predict what this prints?
    return 0;
}

On the other hand, you can create a reference to a pointer. A pointer is simply a value (which happens to be an address) stored in memory, so why shouldn't you be able to create a reference to that piece of memory? For example, you might want to pass a pointer to a function by reference, if you want the function to be able to change the pointer. 

#include <iostream>

int main() {
    int x{1}, y{2};
    int* p = &x;
    int*& r = p;
    r = &y;
    std::cout << *p << std::endl; // Can you predict what this prints?
    return 0;
}

You can even create a pointer to a pointer: 

#include <iostream>

int main() {
    int x{1}, y{2};
    int* p = &x;
    int** q = &p;
    **q = 3;
    *q = &y;
    *p = 5;
    std::cout << x << ' ' << y << std::endl; // Can you predict what this prints?
    return 0;
}

Summary: Pointers vs References

Here are the key differences between pointers and references:

  • A pointer stores an address. A reference is an alias of an existing variable.
  • A pointer can be null. A reference must be bound to a variable.
  • A pointer can be changed to a different address. A reference cannot be reseated.
  • We get the value pointed to by a pointer using the dereferencing operator *. We get the value pointed to be a reference by using the reference directly, just like the original variable.
  • A pointer does not need to be initialized when it is created. A reference does. (But even though it's technically legal to leave a pointer uninitialized, it's good practice to initialize a pointer to nullptr rather than leave it uninitialized.)

The Office Exercise

Using our Employee structure from earlier, write a function topLevelSupervisor which accepts an Employee as argument and returns the Employee's "top-level supervisor" (i.e., the supervisor's supervisor's supervisor's ... until we reach the top of the corporate ladder). Note that an Employee who does not have an assigned supervisor is considered their own top-level supervisor.

Since we haven't covered structures yet, the only thing you need to know about them is that, if e is an Employee, then e.supervisor returns (a pointer to) e's supervisor.

If your functioin works correctly, then the sample code below should identify David Wallace as the top-level supervisor of each Employee in the example. 

#include <iostream>

struct Employee {
    std::string name;
    Employee* supervisor;
};

Employee topLevelSupervisor(const Employee& e) {
    // Write your code here
} 

void printTopLevelSupervisor(const Employee& e) {
    std::cout << e.name << "'s top-level supervisor is " <<
                 topLevelSupervisor(e).name << std::endl;
}

int main() {
    Employee DavidWallace{"David Wallace", nullptr};
    Employee MichaelScott{"Michael Scott", &DavidWallace};
    Employee DwightSchrute{"Dwight Schrute", &MichaelScott};

    printTopLevelSupervisor(DavidWallace);  
    printTopLevelSupervisor(MichaelScott); 
    printTopLevelSupervisor(DwightSchrute);
    return 0;
}

Note that your code works by listing every level of the Employee's supervision: an Employee links to their supervisor, who links to their supervisor, and so on until you reach the top of the corporate ladder. This is an example of a linked list, a data structure that we'll discuss later in the course. In a linked list, we list the items in order by having each item in the list store a link to the next one, rather than by storing items one after the other in an array.

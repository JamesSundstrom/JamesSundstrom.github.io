Before we go back to learning about how to define classes, we're going to take a short break to discuss some other aspects of C++ that become important when defining classes.

Header files

Large-scale software projects can contain millions (or sometimes even billions) of lines of code. This leads to a practical problem: you don't want to wait for all that code to recompile every time you make a tiny change to it. For example, if you make a small change in the implementation of a class that you've defined, you wouldn't want to need to recompile all of the code that uses that class.

Let's take our Polynomial example from the previous lecture. Suppose we have a file program.cpp that uses Polynomial, which is efined in a file polynomial.cpp. We want to be able to compile program.cpp in a way that doesn't depend on the implementation of Polynomial. At first, that might sound impossible: how can the compiler compile code that uses Polynomial without knowing what Polynomial does? But actually, we don't need to know everything about how Polynomial works: we only need to know what attributes and methods the Polynomial class has, so that the compiler knows, e.g., this is an int, this is a method that takes an int as an argument and returns another int, etc. The compiler doesn't need to know specifically how the methods are defined; it can simply leave a "note" to look up the implementation in another file, when needed. Therefore, the compiled code for program.cpp doesn't need to change whenever the implementation of Polynomial changes. Of course, the overall compiled program will need to change, but only the parts of it that come from polynomial.cpp, not the parts that come from program.cpp.

In other words, when the compiler tries to compile program.cpp, it only needs to know the declaration of the Polynomial class, not the actual definitions of the methods. We've already seen that these can be separated: the class can be declared without definitions, and then definitions given later. (Recall that this used the scope resolution operator ::.) Therefore, we need to put the class declaration in one file, with the definitions in a separate file. The declaration goes in a header file, which has a .h extension, while the definitions go in a normal .cpp file. Then, any code that needs to use the class can #include the header file. This allows it to "know" about the class without "knowing" any of the implementation details.

Here's what that might look like for our Polynomial class so far. (We'll add more to it later.)

First, here's the header file polynomial.h: 

#pragma once

#include <vector>
#include <numeric>

class Polynomial {
public:
    Polynomial(const std::vector<int>& coefficients);
    Polynomial(const Polynomial& other);
    Polynomial& operator=(const Polynomial& other);
    ~Polynomial();
    int eval(int n) const;
private:
    int degree_;
    int* coefficients_;
};

We'll discuss the meaning of "#pragma once" later.

Next, here's the .cpp file: 

#include <vector>
#include "polynomial.h"

// Copy the given coefficients vector into coefficients_, while also removing 
// any leading zeros so that degree_ is calculated correctly.
Polynomial::Polynomial(const std::vector<int>& coefficients) {
    int i;
    for (i=0; i < coefficients.size(); ++i) {
        if (coefficients[i] != 0) {
            break;
        }
    }
    degree_ = coefficients.size() - i - 1;
    coefficients_ = new int[degree_ + 1];
    for (int j = i; j < coefficients.size(); ++j) {
        coefficients_[j-i] = coefficients[j];
    }
}

// Copy constructor
Polynomial::Polynomial(const Polynomial& other)
    : degree_(other.degree_), coefficients_(new int[degree_ + 1]) {
    std::copy(&other.coefficients_, &other.coefficients_ + degree_ + 1, &coefficients_);
}

// Copy assignment
Polynomial& Polynomial::operator=(const Polynomial& other) {
    if (this == &other) {return *this;}
    delete[] coefficients_;
    degree_ = other.degree_;
    coefficients_ = new int[degree_ + 1];
    std::copy(&other.coefficients_, &other.coefficients_ + degree_ + 1, &coefficients_);
    return *this;
}

Polynomial::~Polynomial() {
    delete[] coefficients_;
}

int Polynomial::eval(int n) const {
    auto f = [n](int acc, int val) { return acc * n + val; };
    return std::accumulate(coefficients_, coefficients_ + degree_ + 1, 0, f);
}

Notice that when you #include a locally-defined file, you put the name of the file in quotes rather than angle brackets.

Copy the above blocks of code and save them (in the same folder) as polynomial.h and polynomial.cpp.

Now we'll write and compile a program that uses the Polynomial class. For the sake of demonstration, we'll create a very simple test program that calculates f(10) where f(x) = x2 + 5x + 9. Copy the below code and save it (in the same folder) as test.cpp: 

#include <iostream>
#include "polynomial.h"

int main() {
    Polynomial f({1, 5, 9});
    std::cout << f.eval(10) << std::endl; // Should print 159
    return 0;
}

Now let's demonstrate that we can compile the two .cpp files separately. These won't be finished, executable programs: only test.cpp even has a main() to run, and it can't run without the definitions from polynomial.cpp, so we won't get an .exe file. Instead, we'll get object files (.o, or sometimes .obj). Finally, we'll need to link the object files to get our final .exe file.

The flag that tells the compiler to create an object file rather than an .exe file is -c. Run the following command in the terminal to create polynomial.o:

g++ -c polynomial.cpp

Next, run the following command in the terminal to create test.o:

g++ -c test.cpp

If you look in the folder where you saved these files (or use the ls command in the terminal), you should see two new files polynomial.o and test.o. Finally, we can link them together to create test.exe using the following command:

g++ -o test polynomial.o test.o

If everything worked, you should now have a program test.exe which prints 159 when you run it.

A few comments about this:

  • Note that as promised earlier, changing polynomial.cpp would not require us to recompile test.cpp: we were able to compile test.o without making any reference to polynomial.cpp. Indeed, if we change the implementation in polynomial.cpp, we'll need to recompile polynomial.o, and then we'll need to re-link polynomial.o with test.o to create the final .exe, but we won't need to recompile test.o.
  • Of course, there's no need to limit yourself to two .o files. You can list as many files as you need to link. A large software project will almost certainly involve many, many files. (A project like that would also have a system in place to recompile automatically, so you don't need to manually list everything.)
  • You can still compile .cpp files to .exe directly. For example, the below command will create test.exe even if you haven't previously compiled polynomial.o or test.o: g++ -o test polynomial.cpp test.cpp You can even mix-and-match. For example, if you have a pre-compiled polynomial.o and you've just written program test.cpp, you can create test.exe directly: g++ -o test polynomial.o test.cpp

#pragma once

Now we're prepared to talk about why "#pragma once" appeared at the top of our .h file. If you want to see what goes wrong without it, temporarily comment it out, and add an extra "#include "polynomial.h"" at the beginning of test.cpp, so that it's now included twice. If you try to compile the program again (using g++ -o test polynomial.cpp test.cpp), it won't work: you'll get something like "error: redefinition of 'class Polynomial'".

(After you've seen the error, I suggest you undo the changes you just made, so that everything works correctly in case we want to refer back to it again later.)

The problem goes back to something that we talked about on the first day of class. The #include directive is not a "smart" command; it simply tells the preprocessor to copy the contents of the file and paste them directly into your file. If you #include the same file twice, the preprocessor will copy and paste it twice. In this case, that means that the preprocessor copies two declarations of the class Polynomial. The compiler sees two classes both being named Polynomial and raises an error.

At first, this might sound like a minor problem: can't we simply not include the same file twice? But that's actually not so simple. For example, suppose you need to include x.h and y.h, but both of those files have #include <vector>. You'll inevitably end up including vector twice. If we didn't have a way to protect against that situation, it would be impossible to write any program that uses both x.h and y.h.

The line #pragma once that we saw in our polynomial.h file earlier provides that protection. Putting it that the beginning of your .h file tells the preprocessor to only include the code in this file once per compilation, no matter how many times the code tries to include it. Every .h file that you create should include such protection.

There are a couple small problems with using #pragma once:

  • Although virtually all modern compilers support it, it is technically non-standard. If you want to guarantee that your code will work with all C++ compilers, you can't use #pragma once.
  • It sometimes fails to recognize that two included files are the same file, and therefore does not prevent the double-inclusion.

Despite these issues, many programmers consider #pragma once to be good practice. (Others do not -- for example, the Google style guide forbids its use.) I'll allow you to use #pragma once in this course. But you should also be familiar with the older, "official" way of guarding against multiple includes. Here's what it would look like if we used that method on polynomial.h: 

#ifndef POLYNOMIAL_H
#define POLYNOMIAL_H

// Code goes here

#endif

The #define directive is used to define macros, which the preprocessor will replace before compiling the code. For example, you could write "#define PI 3.14159", and then every instance of PI in your code will be automatically replaced with 3.14159. The use of macros is generally discouraged. (For example, you could simply define a constant variable pi, which would then be treated like a normal variable subject to the usual conveniences like typechecking.)

In this case, we don't actually intend to use POLYNOMIAL_H as a macro; instead, we define it simply so that the compiler can see that it's defined. Notice that the entire polynomial.h file is written between #ifndef POLYNOMIAL_H and #endif. The directive #ifndef stands for "if not defined," meaning that the code in between is only included if POLYNOMIAL_H is not already defined. The first time polynomial.h gets included, POLYNOMIAL_H is undefined, so we pass the #ifndef check and include the code normally (along with the #define POLYNOMIAL_H.) If polynomial.h ever gets included again, POLYNOMIAL_H will already be defined, so we won't pass the #ifndef check, and the duplicate code will be ignored.

The downside of this is that, using this technique, every .h file needs to use a different name for its guard. That's why the name is generally based on the filename (and in a bigger project, on the file location), such as our POLYNOMIAL_H above.

For this course, you can use this technique or #pragma once for your include guard. But you must always include one or the other in any .h file you define.

That covers what you need to know about creating a .h file. Now for something completely different...

Lvalues and Rvalues

Every expression in C++ is either an lvalue or an rvalue. The distinction is that an lvalue is something that can appear on the left side of an assignment operator, whereas an rvalue can only appear on the right side. An lvalue must have a name and a permanent address, so that it makes sense to assign a value to it. An rvalue is a temporary value with no name, such as a literal or a result of a calculation. Some examples: 

int main() {
    int x = 5; // x is an lvalue, 5 is an rvalue
    int y = x + 1; // y is an lvalue, x is an lvalue, x + 1 is an rvalue
    int* p = &x; // p is an lvalue, &x is an rvalue
    *p = 42;     // *p is an lvalue, 42 is an rvalue
}

You may have seen an error referring to lvalues and/or rvalues at some point. For example, if you add &x = &y; above and try to compile it, the compiler will probably give you an error message like "error: lvalue required as left operand of assignment"; this is a fancy way of saying that it doesn't make sense to assign to &x (because &x is an rvalue).

Rvalue references

An rvalue reference can be declared just like a regular reference, except that it is declared with && instead of &, and it must be bound to an rvalue. That may sound like a contradiction -- how can we have a reference to a temporary value that is about to be destroyed? We'll see later that they do serve a purpose. But first, a (somewhat contrived) example to illustrate rvalue references in action: 

#include <iostream>

void f(int& x) {
    std::cout << "Permanent value: " << x << std::endl;
}

void f(int&& x) {
    std::cout << "Temporary value: " << x << std::endl;
}

int main() {
    int x{42};
    f(x);    // Permanent value: 42
    f(1729); // Temporary value: 1729
}

When we call f(x), the compiler uses the "Permanent value" version of f; when we call f(1729), the compiler uses the "Temporary value" version. This is an example of overloading, which we'll discuss in more detail later; you can define multiple functions with the same name but different arguments, and the compiler will choose the appropriate one for whatever arguments it's given. In this case, this means that f(x) can use the usual pass-by-reference but can't use rvalue reference because x isn't an rvalue. Conversely, f(1729) can only use the rvalue-reference version but not the ordinary version, because it doesn't make sense to pass a literal by reference.

Aside: If we also defined a pass-by-value version void f(int x), that would cause an error. For each function call, the compiler would have two usable options, and wouldn't know which one to choose.

But that still doesn't answer the main question -- why would we actually want separate functions depending whether the argument is an lvalue or an rvalue?

Move semantics

There's a specific situation where we can take advantage of the knowledge that a function argument is an rvalue -- when we're copying an object. Ordinarily, we would need to copy all of the object's data, so that we don't have two different objects pointing to the same data, which we've seen can lead to problems. But if we're copying an rvalue, then the copied object is about to be destroyed anyway, so we don't need to copy its resources; we can simply "steal" them.

Move constructor

The move constructor lets you construct a new instance of your object based on an existing instance. But the existing instance is an rvalue, so we can steal its resources as described above. We'll see how it works with our Polynomial class: 

Polynomial::Polynomial(Polynomial&& other) noexcept
    : degree_(other.degree_), coefficients_(other.coefficients_) {
    other.degree_ = -1; 
    other.coefficients_ = nullptr;
}

What exactly is happening here?

  • First, the obvious: degree_(other.degree_), coefficients_(other.coefficients_) does exactly what was promised, copying data from other into the new Polynomial. Instead of creating a copy of the coefficient array, it simply takes possession of it.
  • After that, we need to put other into a state where its destruction won't harm us. Most importantly, we need to null out other.coefficients, so that it doesn't get freed when the rvalue is destroyed, because it's now the coefficient array for our newly-constructed Polynomial. Often nothing would go wrong if we didn't change other.degree_, but we can be safe by putting it into a state where we don't expect there to be any coefficients, so that we can't accidentally try to access its coefficients.
  • The noexcept tells the compiler that this method can never throw an exception. (If a function marked as noexcept throws an exception, the program terminates immediately.) It is important to mark the move constructor and move assignment operator (which we'll see next) as noexcept (assuming they can't throw exceptions, which they usually can't). This is because library containers liks std::vector behave differently with classes whose move constructors can/can't throw exceptions; we get better efficiency in the noexcept case, and we need to mark it as such to get that benefit.

Move assignment operator

Just as the copy constructor came with the copy assignment operator, now that we have a custom move constructor, we also need a custom move assignment operator: 

Polynomial& Polynomial::operator=(Polynomial&& other) noexcept {
    if (this == &other) return *this;
    delete[] coefficients_;
    degree_ = other.degree_;
    coefficients_ = other.coefficients_;
    other.degree_ = -1;
    other.coefficients_ = nullptr;
    return *this;
}

Unsurprisingly, this looks a lot like the code for the move constructor, except that when we assign a new value to an existing object, we need to delete the old data first.

std::move

Hopefully you're convinced that being able to steal resources from an object that's about to be deleted is a nice trick to make your code a little more efficient. So far, we can only steal from rvalues, because their imminent deletion is guaranteed. But C++ gives us as programmers a lot of power to handle memory ourselves -- you might guess that we have the ability to tell the compiler to steal from an lvalue, trusting us that the lvalue won't be used again (at least not until it's reinitialized). This can be done using std::move.

The function std::move can be included via #include <utility>. It casts an lvalue to an rvalue reference, so that you can steal resources from it. The name is a bit of a misnomer -- std::move doesn't move anything itself, only give permission to move resources.

Warning: There's a different std::move defined in the algorithm header. It's fine to include both headers at once, because the two std::move functions take different arguments, so the compiler can distinguish them. But if you're ever confused why std::move isn't working even though std::move exists, check whether you included algorithm instead of utility.

We can demonstrate this using our Polynomial class. (Make sure you've copied the new code into polynomial.h and polynomial.cpp.) 

#include <iostream>
#include <utility>
#include "polynomial.h"

int main() {
    Polynomial f({1, 5, 9});
    Polynomial g({2, 6});
    std::cout << f.eval(10) << std::endl; // 159
    f = std::move(g);
    std::cout << f.eval(10) << std::endl; // 26
    std::cout << g.eval(10) << std::endl; // 0
    return 0;
}

Lecture 14: Linked Lists, Stacks, and Queues

Linked lists

We've already discussed the basic concept of a linked list: a list where each piece of data is contained in a node that also holds a pointer to the next piece of data. This simple version can also be called a singly-linked list because the links only go in a single direction: forward. For some applications, that's good enough, but in other cases you might want to go backwards through the list also. In a doubly-linked list, each node carries a pointer to the previous and the next pieces of data, so you can easily navigate in either direction. However, you can't efficiently subscript into the list (i.e., use v[i] to access the ith element). The only way to access the ith element is to go through the list one-by-one: the data at index 0 links to the data at index 1, which links to the data at index 2, and so on. Therefore, it takes $O(i)$ time to access the $i$th entry, which in the worst case in $O(N)$ for a list of length $N$.

The LinkedList class that we created in Lecture 08 was fairly minimal: the LinkedList class itself only had one attribute, a pointer to the first ListNode. This means that it's fairly easy to insert an item at the beginning of the list, or to read existing data from the beginning of the list, but potentially time-consuming to insert/read at the end of the list, because the only way to find the end of the list is to iterate through the entire list. If that's something that you need to be able to do efficiently, your LinkedList class could also hold a pointer to the last ListNode.

Conversely, some extremely simple linked list implementations don't provide a LinkedList class at all, only a ListNode class. (After all, our simple LinkedList class only held a pointer to the first ListNode, so why not skip the LinkedList class and just use the pointer directly?) This is generally how LeetCode handles linked lists.

Benefits/drawbacks of a linked list

You might wonder why we care about linked lists? Why not just use an array/vector, which gives us the convenient v[i] syntax? The major advantage of a linked list is that it allows for efficient insert/delete operations.

If you want to insert a new piece of data at the beginning of an array of size $N$, that's a $O(N)$ operation: all of the other data needs to be shifted one space over to make room for the new data. But in a linked list, insertion at the beginning (or end, assuming the linked list carries a pointer to the end) is a $O(1)$ operation: you just create the new node and update a couple pointers appropriately. Inserting at the end of a std::vector is an amortized $O(1)$ operation, but as we've seen, sometimes an individual insertion is $O(N)$. If you need a guarantee that the insertion will be fast every time, a linked list provides that.

A similar observation is true if you want to insert in the middle of the list. Doing that with an array requires moving (potentially) a lot of data, while doing that with a linked list only requires updating a few pointers. The downside with a linked list is that, if you want to insert at index $i$, that might be costly anyway, because it takes $O(i)$ steps just to find that part of the list. But if you already have a pointer to the location that you want to insert, then insertion anywhere in a linked list is $O(1)$.

Another benefit of linked lists is that you can insert/delete data without invalidating existing iterators. In an array, if you have an iterator that points to the data at index 50, and then you insert/delete data at index 22, that moves all the subsequent data, so arr[50] no longer points to the same data. On the other hand, with a linked list, the iterator is effectively a pointer to the corresponding ListNode, so no matter what other data you insert/delete, the iterator will still point to the same data.

On the other hand, the main drawback of a linked list is lack of random access: you can't quickly access the ith entry in a linked list. Another drawback is that a linked list uses extra memory compared to an array, since the linked list needs to store extra pointers. One final drawback is that a linked list doesn't store its data in continuous memory, so it takes longer for the hardware to work with a linked list than an array; in practice, this can sometimes cancel out the theoretical benefits of a linked list.

std::list

The standard library provides std::list (in the list header), which is a doubly-linked list that includes pointers to the beginning and end so that you can access either side easily. You can use the .front() and .back() methods to access the values in the front or the back, and .push_front(), .pop_front(), .push_back(), and .pop_back() to insert/remove (push/pop) data at the front or back. It also has .begin() and .end() methods that return iterators so it can be used with all the algorithms in the algorithm header. If you have an iterator into the list, then the .insert() and .erase() methods will insert/erase data there. (Remember that inserting at the ith position is potentially inefficient if you need to start from the beginning, but extremely efficient if you already have an iterator pointing to the ith position. That's why .insert() and .erase() take iterators as arguments.)

You can see the documentation for std::list here.

Stacks

We've discussed stacks before: a stack is a LIFO (last in, first out) container, meaning that you can only directly access the most-recently added data. You can think of it as a stack of physical objects: the only one that's convenient to access is the top item.

As it turns out, there are many real-world problems where that's all you need. For example, the stack that C++ uses for memory management: if a function f calls a function g which calles a function h, then h needs to be resolved first, then g, then f, so it makes sense that the stack frames for these functions are stored in a stack. Another important application is the "undo" ability in an editing program. The program keeps track of all the edits that you've made. When you need to undo them, you undo the most-recent edit first, so it makes sense that the edits are tracked in a stack. (Then the undone edits can be stored in a separate "undo stack" in case you decide to redo them later.)

You may recall that our simple LinkedList class from Lecture 08 implemented a stack: we could only insert/remove data at the head, so the first accessible data was always the last data entered. (While using a linked list to implement a stack is a classic textbook problem, it's actually not how stacks are usually implemented in real-world applications.)

The core operations for a stack are:

  • .push(value): Add a value to the top of the stack.
  • .top(): Return the top value (without removing it).
  • .pop(): Remove the top value from the stack (without returning it).
  • .empty(): Return true or false depending whether the stack is empty.

A simple implementation of a stack is given below. (To keep it simple, we've skipped all the non-delete Rule of Five methods.) 

template <typename T>
class Stack {
public: 
    Stack() : capacity_(16), size_(0), data_(new T[capacity_]) {}
    
    ~Stack() {
        delete[] data_;
    }

    void push(const T& val) {
        if (size_ == capacity_) grow();
        data_[size_] = val;
        ++size_;
    }

    T& top() {
        return data_[size_ - 1];
    }

    const T& top() const {
        return data_[size_ - 1];
    }

    void pop() {
        if (size_ > 0) 
            --size_;
    }

    bool isEmpty() {
        return size_ == 0;
    }

private:
    int capacity_;
    int size_;
    T* data_;
    
    void grow() {
        T* oldData = data_;
        capacity_ *= 2;
        data_ = new T[capacity_];
        for (int i = 0; i < size_; ++i) {
            data_[i] = oldData[i];
        }
        delete oldData;
    }
};

Note that we've implemented two versions of .top(), a const and a non-const version. This way, .top() still works for a const Stack. (Of course, a const Stack wouldn't make much sense. But you might want a const reference to a Stack.)

Aside: This version is closed to how the standard library implementation of stack works than our linked list version was, but it's still a bit of an oversimplification.

Queues

Queues are similar to stacks, but instead of being LIFO, they are FIFO (first in, first out). Similar to stacks, the core operations are:

  • .push(value): Add a value to the end of the queue.
  • .front(): Return the front (first-added) value (without removing it).
  • .pop(): Remove the front value from the stack (without returning it).
  • .empty(): Return true or false depending whether the queue is empty.

Trying to implement a queue using arrays would be messy, since deleting from the 0-indexed side of the array is time-consuming. (Or if you tried to use the 0-indexed side as the back of the queue, inserting would also be time-consuming.) A linked list would probably be better (though again, that's not what's typically used in practice.)

As you might expect, the standard library has a std::stack type, which you can read about here.

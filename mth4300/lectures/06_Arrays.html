Lecture 06: Arrays

An array is the C++ equivalent of Python's list type. However, there are some key differences. Unlike Python, C++ doesn't let you store objects of different types together in the same array. You've already seen this principle in C++ with std::vector<T>: you need to specify the type T of objects that the vector or array will contain.

Aside: The C++ mechanism that lets you use std::vector and similar classes with whatever type of data you want is called a called a template. We'll talk more about templates later, but for now it's enough for you to be aware that when you see syntax like this, it indicates that the code will work polymorphically with different classes.

Another important difference between C++ arrays and Python lists is that C++ arrays can't be resized after they're created. As we've seen before, std::vector<T> is resizable, so you can use that if you need a resizable list.

The last important difference is another one we've seen before: C++ does not check array bounds. If arr is an array of size 5, then arr[-1] and arr[5] lead to undefined behavior. (As usual, arrays are 0-indexed, so 5 is out of bounds for an array of size 5.)

There are actually two different types of arrays in C++: the old-fashioned C-style array and the more modern std::array. You should use std::array in your code. It's just as efficient, and it provides modern conveniences that make your code easier to write and understand. Nonetheless, we're going to require you to learn about C-style arrays in this course. For one thing, there is some C++ code that uses C-style arrays, and if you become a professional programmer, you may need to deal with old code that uses C-style arrays, even if you never write such code yourself. Relatedly, you may want your C++ code to be able to interface with C code, or you may even want to write C code yourself, in which case you'll need to understand C-style arrays.

Declaring C-style arrays (on the stack)

You can declare an array of objects of type T in exactly the same way that you declare a single object of type T, except that after the variable name, you put the size of the array in brackets. 

#include <iostream>

int main() {
    int squares[6] = {0, 1, 4, 9, 16, 25}; // Declare and initialize
    for (int square : squares) {
        std::cout << square << ' ';
    }
    return 0;
}

As with other variables, you can also declare an array without initializing it. Of course, you still need to initialize the data before trying to access the values, or you'll get undefined behavior. 

#include <iostream>

int main() {
    int squares[5]; // Declare without initializing
    for (int i = 0; i < 5; ++i) {
        squares[i] = i * i; // Now initialize
    }
    for (int i = 0; i < 5; ++i) {
        std::cout << squares[i] << ' ';
    }
    return 0;
}

Note that when you declare an array like this, the size of the array must be known at compile time. This is because the array is stored in stack memory and, as we discussed earlier, the compiler always needs to know exactly how much memory everything on the stack will use. You can't create an array on the stack if you don't know how many items it will hold. (Later, we'll see how you can create an array on the heap, which allows you to create an array whose size isn't known until runtime.) For example, the following code is illegal according to the C++ standard: 

#include <iostream>

int main() {
    int size;
    std::cout << "Enter a non-negative integer: "; 
    std::cin >> size;
    int squares[size];
    for (int i = 0; i < size; ++i) {
        squares[i] = i * i;
    }
    for (int s : squares) {
        std::cout << s << ' ';
    }
    std::cout << std::endl;
    return 0;
}

Some compilers may actually allow you to compile this code, but you still shouldn't write it; it's an extremely bad idea to write nonconforming code that only works with certain compilers. For example, I can compile this code using: 

g++ -o example example.cpp

However, if I turn on the compiler option to warn me about nonconforming code, I get a warning: 

g++ -o example example.cpp -Wpedantic

There are other options -Wall and -Wextra that you can turn on to get more warnings, and an option -Werror that turns all warnings into errors that prevent compilation. It's a good idea to compile your code with these options turned on, so that you can't accidentally compile nonconforming code: 

g++ -o example example.cpp -Wpedantic -Wall -Wextra -Werror

If you try to compile the above example with these options, it won't compile.

It is also against the C++ standard to declare an array whose size is a non-constant variable. With the strict options above turned on, the following code won't compile: 

#include <iostream>

int main() {
    int size = 10;
    int squares[size]; // Still against the C++ standard!
    for (int i = 0; i < size; ++i) {
        squares[i] = i * i;
    }
    for (int s : squares) {
        std::cout << s << ' ';
    }
    std::cout << std::endl;
    return 0;
}

However, if the variable representing the size is declared as a const, then the compiler can replace the variable with its (known, constant) value, and the code becomes legal. In fact, this is often good practice: instead of using a "magic number" for the size of your array, give it a helpful name. The following code is legal: 

#include <iostream>

int main() {
    const int size = 10;
    int squares[size]; // This is fine
    for (int i = 0; i < size; ++i) {
        squares[i] = i * i;
    }
    for (int s : squares) {
        std::cout << s << ' ';
    }
    std::cout << std::endl;
    return 0;
}

(Of course, this code is just for demonstration. If we actually wanted to write a program to print out the first few squares, we should just calculate and print them one at a time; there's no reason to store them all in an array first.)

Arrays, pointers, and pointer arithmetic

An array decays to a pointer, which means that if an array is provided somewhere that a pointer is expected, it is converted to a pointer to the first element of the array. For example, if nums is an array of ints, then int *p = nums is equivalent to int *p = &nums[0].

However, you should remember that this decay is a type conversion: an array is not a pointer. For example, we can't reassign an array as we would a pointer: 

int main() {
    int x{1}, y{2};
    int *p = &x, *q = &y;
    p = q; // Legal

    int z[5] = {1, 2, 3, 5, 8}, w[5] = {2, 3, 5, 7, 11};
    z = w; // Illegal
    return 0;
}

Another difference is that we can use sizeof to get the correct size of an array (in bytes), which wouldn't work if we had only the pointer to the first element: 

#include <iostream>

int main() {
    int nums[5] = {1, 2, 3, 5, 8};
    int* ptr = &nums[0];
    std::cout << sizeof(nums) << std::endl; // Prints 20 (assuming an int is 4 bytes)
    std::cout << sizeof(ptr) << std::endl;  // 
    return 0;
}

In fact, you can even use pointers to access the elements of an array. To understand why and how this works, you need to understand pointer arithmetic. If ptr is a pointer to an object of type T and n is an integer, then the code ptr + n corresponds to the number ptr plus n * sizeof(T). For example, the below code should print two numbers that differ by 16 (since pointers print in hexadecimal, this means they'll probaby differ by 1 in the 16's place.) 

#include <iostream>

int main() {
    int nums[5] = {1, 2, 3, 5, 8};
    int *ptr = nums;
    std::cout << ptr << std::endl;
    std::cout << ptr + 4 << std::endl;
    return 0;
}

Of course, the same rule applies if you try to do subtraction an integer from a pointer, or if you try to apply the increment/decrement operators to a pointer. If you subtract two pointers, you get the difference between them divided by sizeof(T). 

#include <iostream>

int main() {
    int nums[5] = {1, 2, 3, 5, 8};
    int *p = nums;
    int *q = nums + 3;
    std::cout << p << std::endl;
    std::cout << q << std::endl; // Prints something 12 greater than the previous output
    std::cout << q - p << std::endl; // Prints 3, not 12
    return 0;
}

You can't add a pointer to another pointer, but why would you ever want to?

The purpose of defining pointer arithmetic this way is that it allows you to traverse arrays using pointers. For example, if arr is an array and p is a pointer to arr[i], then p + n is a pointer to arr[i+n]: the array stores the data in arr in contiguous memory, so increasing an address by sizeof(T) bytes hops over exactly one T and advances us to the next item in the array. Since adding n to a pointer corresponds to increasing the pointer by sizeof(T) n times, this moves us forward n items in the array. Similarly, if p is a pointer to arr[i] and q is a pointer to arr[j], then q - p returns j-i, the "distance" (in plain English, not in bytes) between the two array entries.

To summarize, if p is a pointer to arr[0], then p + n is a pointer to arr[n]. If we wanted to, we could access arr[n] as *(arr+n); in fact, this is the definition of arr[n]. Since addition is commutative, this also means that n[arr] is also equivalent to arr[n]! (Of course, you generally shouldn't write *(arr+n) and you definitely should never write n[arr]-- try your best to make your code easily understandable!)

Array decay

When you pass a C-style array as an argument to a function, the array decays into a pointer to the first element. In other words, even if you declare a function as void f(int arr[]), it will still act like void f(int *arr). Sometimes, this doesn't matter -- as we saw above, nums[i] does the same thing regardless of whether nums is an array or a pointer. But it does matter in a very important way -- by decaying into a pointer to the first element, we've lost the information about the size of the array. We no longer have any clue where the array ends! As a result, we can't use sizeof to get the size of the array inside a function: 

#include <iostream>

void printSize(int arr[]) {
    std::cout << sizeof(arr) << std::endl;
}

int main() {
    int nums[9] = {1, 2, 3, 5, 8, 13, 21, 34, 55};
    std::cout << sizeof(nums) << std::endl; // Prints 36
    printSize(nums);                        // Prints 8
    return 0;
}

This also means that we can't iterate over the array, because it's meaningless to iterate over a pointer. For example, the below code won't compile: 

#include <iostream>

void print(int arr[]) {
    for (int n : arr) {
        std::cout << n << ' ';
    }
}

int main() {
    int nums[9] = {1, 2, 3, 5, 8, 13, 21, 34, 55};
    print(nums); 
    return 0;
}

Even if we tried to use an index-based for loop instead, we still couldn't get the print function to work because it simply hasn't received enough information -- it knows where the array starts, but not where it ends. The simplest solution is to pass the size of the array as a separate argument, so that print has the information it needs: 

#include <iostream>

void print(int arr[], int size) {
    for (int i = 0; i < size; ++i) {
        std::cout << arr[i] << ' ';
    }
}

int main() {
    const int size = 9;
    int nums[size] = {1, 2, 3, 5, 8, 13, 21, 34, 55};
    print(nums, size); 
    return 0;
}

Technically, you can pass a C-style array as an argument to a function without decay by using templates, but that's more advanced, and you won't need to know how to do that for this course. After all, you shouldn't even be using C-style arrays in your own code. 

#include <iostream>

template <typename T, std::size_t N>
void print(T (&arr)[N]) {
    for (T i : arr) {
        std::cout << i << " ";
    }
}

int main() {
    int nums[9] = {1, 2, 3, 5, 8, 13, 21, 34, 55};
    print(nums); 
    return 0;
}

Similarly, a C++ function cannot return a C-style array, only a pointer to the first element of the array. Again, the easiest solution to this problem is simply not to use C-style arrays: use the C++ standard library std::array or std::vector.

But if we want our functions to be able to return arrays, we actually have an even bigger problem to deal with first. Without reading ahead, can you figure out what's wrong with the following code? 

#include <iostream>
#include <cmath>

int* digitPowers(int n) {
    int s[10];
    for (int d = 0; d < 10; ++d) {
        s[d] = pow(d, n);
    }
    return s;
}

int main() {
    int* digitCubes = digitPowers(3);
    for (int i = 0; i < 10; ++i) {
        std::cout << digitCubes[i];
    }
    return 0;
}

The function digitPowers returns the array s, which decays to a pointer to s when it's returned. But s is a local variable that digitPowers created on the stack, which gets destroyed as soon as digitPowers returns. So (if this code compiles at all), digitPowers is giving you garbage, a memory address for a block of memory that's no longer allocated to our array.

If we want to solve this problem, we finally need to learn how to allocate memory on the heap.

Allocating on the heap

We've seen that variables allocated on the stack need to be destroyed when the function that created them is destroyed, and that the compiler needs to know exactly how much memory to allocate for them. But frequently, we want to allocate memory that doesn't meet those criteria. For example, we might need to allocate an array whose size won't be known until runtime, because it's based on user input. Or, as in the digitPowers example above, we might want an object to outlive the function that created it. In cases such as these, we need to use heap memory instead.

You can allocate memory on the heap using new, which returns a pointer to the allocated memory. Here's an example which (for no good reason other than demonstrating new) allocates two ints on the heap: 

#include <iostream>

int main() {
    int* p = new int{1729}; // Allocate an int on the heap, and initialize it to 1729
    int* q = new int;       // Allocate an int on the heap, uninitialized
    *q = 1234;              // As usual, we must initialize a variable before we use it
    
    std::cout << *p << ' ' << *q << std::endl; // Prints 1729 1234

    delete p;
    p = nullptr;
    delete q;
    q = nullptr;

    return 0;
}

After we're finished using a variable that's allocated on the heap, we need to delete it manually. Many other programming languages, including Python, provide what's known as garbage collection: when an object is no longer referenced by any variable, so that the program can no longer use it, the object is automatically deleted from memory. This ensures that the memory isn't filled with objects that we've finished using, so that we don't run out of memory due to storing garbage.

The benefit of automatic garbage collection is obvious: the programmer doesn't have to keep track of when an object is no longer needed and delete it manually. But garbage collection has a downside: your program is doing a lot of behind-the-scenes work to keep track of whether each object is still needed, and all that extra work could affect performance. If it does start to affect performance at an inconvenient moment, you as the programmer have no way to deal with that, since you don't control when garbage collection occurs. C++ has decided to adopt the opposite philosophy: give the programmer control over when objects on the heap are deleted. The programmer now has more control over the performance of the program, at the cost of more effort while writing the code.

When you're done using a heap-allocated object, you need to delete it; if you don't, that's a memory leak. If that happens too often (say, you have a memory leak inside a long-running loop), your program could eventually run out of memory and crash. Thus, in the above example, we deleted the objects on the heap when we were done with them using delete p and delete q.

After deleting p and q, we set them both to nullptr. While this is not technically necessary, many C++ programmers and style guides consider it best practice. It's a safety measure: you don't want to accidentally use p to access a memory block that no longer stores the object you expect, so you null out p to prevent that from happening. This also protects you from accidentally calling delete on the same pointer twice. Double-deleting a pointer is undefined (and often difficult to debug) behavior, so we want to avoid that; using delete on nullptr does nothing by definition, so it won't cause any problems. (At least, it won't cause any new problems -- you should still figure out how you got a double-delete in the first place, because it might be a sign of a more serious bug.)

If we don't use delete, we get a memory leak. Below is an example of a memory leak. In this case, it's benign, because the program ends immediately anyway. But something like this could cause a problem in the context of a larger program. 

int main() {
    int* p = new int{1729}; 
    p = nullptr; // Memory leak! We have no pointer to 1729, so it can't be freed
    return 0;
}

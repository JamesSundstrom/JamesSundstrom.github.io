Lecture 13: Asymptotic Notation

Motivation

When we write algorithms in computer science, there are two measurements that we often care about: how much time the program takes to run, and how much memory it needs. More precisely, we're generally interested in the runtime and memory as a "function" of the size of the input. Of course, it won't be a true function in the mathematical sense because there's isn't a well-defined output for each input -- inputs of the same size could take different amounts of time to run. But thinking of it as a function won't do any harm.

For example, suppose I give you a std::vector of length $N$ and ask you whether it contains a particular value. The runtime could be extremely fast -- maybe the value we're looking for is the first entry in the vector. But the worst-case scenario is if the value isn't in the vector. Then we need to check every single entry before we can be sure that it isn't present, which requires $N$ checks.

We could also ask how long it takes to sort a vector of length $N$, or how long it takes to crack an encryption where the key has length $N$. In all of these cases, we're interested in understanding the performance of our program as a "function" of $N$.

But we cannot calculate the exact amount of time or memory required. For example, the amount of time that a program takes to run will depend on many factors, such as the machine that is running it, what other programs are running at the same time, what optimizations the compiler made, and even a bit of luck. For example, our vector-search algorithm above requires $N$ comparisons in the worst-case scenario, but how long each of those comparisons takes will depend on how fast your computer is. (It will also depend on exactly what's being compared: checking whether two strings are equal is more complicated than checking whether two characters are equal.) For that reason, we'll usually speak in terms of the number of computations required rather than the number of seconds required.

Fortunately, we don't really care about the exact numbers. To see why, suppose we write two different versions of a program, one of which takes twice as long to run as the other version. Twice as long sounds like a pretty difference. But in the grand scheme of things, it probably isn't. Maybe both programs are fast enough that they appear essentially instantaneous to humans, so it doesn't matter which one is faster. Even if the faster program takes a day to run, so the slower program takes two days, that might be okay -- if it's okay to wait one day for your results, there's a decent chance that it's okay to wait two days. For example, if you're a spy agency trying to crack somebody's encryption to read their emails, it probably won't make a huge difference whether that takes one day or two. Somebody trying to keep their email secure doesn't really gain much security by switching to an encryption key that takes twice as long to crack; they want a key that takes many, many times longer.

In other words, if one algorithm requires $N^2$ computations, and the other algorithm requires $2N^2$ computations, we want to think of those algorithms as requiring essentially the same amount of time. On the other hand, if one algorithm requires $N^2$ computations and the other requires $N^3$ computations, then the latter takes $N$ times as long. For example, if $N=1000$, then the slower algorithm takes 1000x as long to run. And $N=1000$ isn't even particularly large in a lot of applications: a real-world dataset could easily contain millions of data points, where the slower algorithm might take 1,000,000x as long.

So that's the problem we want to solve. We want to understand how much time/memory our programs will require as a "function" of $N$, and we want to be able to write our answer in a way that looks at the "big picture" of how the performance depends on $N$, without getting bogged down in relatively minor details like constant factors, so that $N^2$ and $2N^2$ are "basically the same," whereas $N^2$ and $N^3$ are meaningfully different. Fortunately, mathematicians have a notation that does exactly this.

Big-$O$ Notation

Definition: We write $f(x) = O(g(x))$ (pronounced "$f$ equals big-$O$ of $g$") to mean that there exists a constant $C$ such that, for all sufficiently large $x$, $|f(x)| \le Cg(x)$.

The idea behind this notation is that $f$ will usually be a complicated function that we're trying to study, while $g$ will be a simpler function that we understand well. Thus, the big-$O$ notation allows us to "replace" the original, complicated function with something easier to understand. Theoretically, it's perfectly legal to write $f(x) = O(g(x))$ where $f$ is a simple function and $g$ is a complicated function, but in practice there's virtually never any reason to do that.

First, notice that this definition does what we wanted in terms of ignoring minor details like constant factors. For example, it's true that $2N^2 = O(N^2)$, because the above definition is satisfied with $C=2$. Realistically, the number of computations required for an algorithm won't usually come out to a nice simple formula like $2N^2$; maybe it'll be something like $2N^2 + 5N + 3$. Big-O notation handles that nicely too. We can see that $2N^2 + 5N + 3 = O(N^2)$, using a constant $C=10$:

\[2N^2 + 5N + 3 \leq 2N^2 + 5N^2 + 3N^2 = 10N^2. \]

Pedantic point: The above inequality isn't true when $N=0$. Fortunately, we don't really care about that in computer science. We can assume that any reasonable algorithm will be fine for small inputs, so we only worry about large inputs. We don't need to care that, when $N=0$, an algorithm that requires $2N^2 + 5N + 3$ computations will be slower than an algorithm that requires $10N^2$ computations, because either algorithm is essentially instantaneous when it's given an input of size 0. This is why our definition of big-$O$ notation only required that $|f(x)| \le Cg(x)$ for sufficiently large $x$; we can ignore small values of $x$ (or in this case, $N$) to focus on the important details.

So now we've seen that big-$O$ notation is powerful enough to let us abstract away minor details by writing things like $2N^2 + 5N + 3 = O(N^2)$. But now we have to worry about the opposite problem: what if it's too powerful, and it lets us abstract away details that actually matter? For example, we said above that an algorithm requiring $N^3$ steps is, in a meaningful way, worse than an algorithm that requires $N^2$ steps, so we do not want $N^3 = O(N^2)$ to be true. Let's make sure that's the case:

Proof that $N^3 \neq O(N^2)$: In order for $N^3 = O(N^2)$ to be true, there would need to be some constant $C$ such that $N^3 \leq CN^2$ for all large $N$. Dividing by $N^2$, this is equivalent to the claim that $N \leq C$ for all large $N$. But obviously that's nonsense: in fact, $N > C$ for all large $N$.

There's a detail here that can be a little bit confusing: $N^3 \neq O(N^2)$, but it is true that $N^2 = O(N^3)$. (Indeed, we can check that the definition is satisfied with $C=1$, because $N^2 \leq N^3$ for all $N\geq 1$.) At first, this might seem like a problem with the notation: we wanted $N^2$ and $N^3$ to be "different," but now we're allowed to say that $N^2 = O(N^3)$. But actually, that's not a problem. Big-$O$ notation was never meant to say that $f$ and $g$ are the same. Remember that the definition of $O$ used a $\leq$ for the comparison; saying that $f(x) = O(g(x))$ says only that that $f$ isn't "too big" compared to $g$, but there's nothing preventing $f$ from being much smaller. If you're writing a program and you realize that you need an algorithm that takes $O(N^3)$ steps to solve a certain problem in order for your program to run quickly enough, you're not going to be upset if someone gives you an algorithm that takes $N^2$ steps. Of course, we wouldn't go out of our way to write something like $2N^2 + 5N + 3 = O(N^3)$, because $2N^2 + 5N + 3 = O(N^2)$ is more informative. But we don't need to be upset about the fact that $2N^2 + 5N + 3 = O(N^3)$ is true.

Hopefully, you're now convinced that big-$O$ notation does what we wanted. Next, we want to develop some intuition for how it works. Previously, we proved that $2N^2 + 5N + 3 = O(N^2)$ by writing out the inequality $2N^2 + 5N + 3 \leq 2N^2 + 5N^2 + 3N^2 = 10N^2$, but you can imagine that this would get tedious very quickly for more complicated functions. Fortunately, once you develop a little intuition for big-$O$ notation, you almost never need to write out inequalities and find $C$ explicitly.

The key intuition behind big-$O$ notation is that it captures the order of growth of the function. In other words, we use big-$O$ notation to describe how fast a function grows by comparing it to a simpler function whose growth is well-understood. As such, if our function contains multiple terms, we (almost always) need only look at the term that grows the fastest. For example, in $2N^2 + 5N + 3$, we know that $N^2$ grows much faster than $N$ or than $3$ (which doesn't grow at all), so we can intuitively predict that the $2N^2$ term will be relevant, while the $5N+3$ will not. If you have good intuition about the growth rates of different functions, you can generally predict which term will be important.

For example, we know that if $d > e$, then $N^d$ grows faster than $N^e$. Hence if $f(N)$ is a polynomial, the leading term (i.e., highest-degree term) of $f(N)$ is the fastest-growing, so it will be the term that's relevant if we want to use big-$O$ notation to talk about $f$:

Theorem: If $f(N)$ is a polynomial of degree $d$, then $f(N) = O(N^d)$.

Proof: We know from Calc I that $\lim_{N\to\infty} f(N)/N^d$ exists; denote the limit by $L$. This means that $f(N)/N^d \approx L$ for all large $N$, so $\lvert f(N) \rvert/N^d \lt \lvert L\rvert + 1$, which proves that $f(N) = O(N^d)$ using the constant $C = \lvert L \rvert + 1$.

Applying big-$O$ notation to computer programs

Now let's start trying to use big-$O$ notation to analyze real algorithms. We'll start with an extremely basic one: if you're given a std::vector<int> of length $N$ and you want to check whether a given value appears in the vector, how would you express the runtime of that algorithm in big-$O$ notation?

Answer: $O(N)$. Obviously the worst-case scenario is if you need to check every single entry in the vector, i.e., you need to make $N$ checks. The actual number of instructions executed by the computer will be greater than $N$; there's going to be an iterator that keeps track of where we are in the vector, which will also need to be updated every iteration. But if each iteration involves $c$ steps, the total number of steps will be $cN$, which is still $O(N)$. In practice, we don't bother saying all that when we're analyzing the runtime of the algorithm, you can just say that the runtime is obviously $O(N)$, without including an explanation of how iteration works and why it doesn't affect the big-$O$ notation.

Consider the following function, which attempts to whether a target number can be written as the sum of any two numbers in a vector of length $N$ (allowing the same number to be repeated twice). How would you write its runtime in big-$O$ notation? 

#include <vector>
bool isSum(int target, std::vector<int> v) {
    for (int a : v) {
        for (int b : v) {
            if (a + b == target) {return true;}
        }
    }
    return false;
}

If target is not in the vector, then this code runs through all pairs of a and b. Since there are $N$ values of a and $N$ values of b, there are $N^2$ pairs. Therefore this algorithm is $O(N^2)$.

You might object that this algorithm can be improved: we're running through all pairs, but that's not really necessary. Since addition is commutative, it's a waste of time to check a + b and later check b + a again. We can write a more efficient algorithm by only looking at pairs v[i], v[j] with i >= j. What can we say about the runtime for this algorithm? 

#include <vector>
bool isSum(int target, std::vector<int> v) {
    for (int i = 0; i < v.size(); ++i) {
        for (int j = 0; j <= i; ++j) {
            if (v[i] + v[j] == target) {return true;}
        }
    }
    return false;
}

When i is 0, we consider one j value (0). When i is 1, we have two j values (0 and 1). Continuing in this fashion, we see that each i contributes i+1 pairs, so the total number of pairs we need to check in this algorithm is $1+2+\dotsb+N=N(N+1)/2$. This is an improvement over $N^2$, but still a $O(N^2)$ algorithm.

You might be wondering how we knew that $1+2+\dotsb+N=N(N+1)/2$. This is a finite arithmetic series, so if you remember the formula for the sum of an arithmetic series, you could solve the problem that way. Alternatively, note that

\[ 2(1+2+\dotsb+N) = (1+2+\dotsb+N) + (N+(N-1)+\dotsb+1) = (1+N) + (2+N-1) + \dotsb + (N+1) = N(N+1). \]

Fortunately, you don't need to know this exact formula; you only need to know the fact that $1+2+\dotsb+N=O(N^2)$. One way to see this is to imagine drawing $1+2+\dotsb+N$ dots in a triangular array; thus the total number of dots is approximately the area of a triangle with base $N$ and height $N$, which gives us a quick way to estimate that $1+2+\dotsb+N$ is approximately proportional to $N^2$, since area is proportional to the square of side length. But sums like this come up fairly often when we're analyzing algorithms with nested loops, so we'd like a quick way to estimate them in general. The following theorem gives us that:

Theorem: If $f$ is a polynomial of degree $d$, then $f(1) + f(2) + \dotsb + f(N)$ is a polynomial of degree $d+1$. Therefore, $f(1) + f(2) + \dotsb + f(N) = O(N^{d+1})$.

Similarly, if we wanted to modify the previous function to check whether the target is a sum of three numbers in the vector, that would be a $O(N^3)$ algorithm: 

#include <vector>
bool isSum(int target, std::vector<int> v) {
    for (int i = 0; i < v.size(); ++i) {
        for (int j = 0; j <= i; ++j) {
            for (int k = 0; k <= j; ++k)
                if (v[i] + v[j] + v[k] == target) {return true;}
        }
    }
    return false;
}

The inner two loops check whether target - v[i] can be written in the form v[j] + v[k], with k <= j <= i. We saw above that this takes $O(i^2)$ time. Therefore, by the theorem, the whole algorithm takes time $O(1^2 + 2^2 + \dotsb + N^2) = O(N^3)$.

We could continue this pattern and see that the naive algorithm to check whether target can be written as a sum of $k$ numbers from a vector of length $N$ takes time $O(N^k)$. Can you think of an algorithm that would be more efficient?

What if we wanted to check whether a number can be written as a sum of 1, 2, or 3 entries in a vector? We could implement that simply by checking the cases 1, 2, and 3 separately: 

#include <vector>
bool isSumOfAtMostThree(int target, std::vector<int> v) {
    for (int i = 0; i < v.size(); ++i) {
        if (v[i] == target) {return true;}
    }
    for (int i = 0; i < v.size(); ++i) {
        for (int j = 0; j <= i; ++j) {
            if (v[i] + v[j] == target) {return true;}
        }
    }
    for (int i = 0; i < v.size(); ++i) {
        for (int j = 0; j <= i; ++j) {
            for (int k = 0; k <= j; ++k)
                if (v[i] + v[j] + v[k] == target) {return true;}
        }
    }
    return false;
}

The first loop takes $O(N)$ steps, the second (nested) loop takes $O(N^2)$ steps, and the third (nested) loop takes $O(N^3)$ steps. Therefore the total algorithm takes $O(N + N^2 + N^3) = O(N^3)$ steps.

This is an example of the general fact that if an algorithm consists of first running a subalgorithm that takes $O(f(N))$ steps followed by a subalgorithm that takes $O(g(N))$ steps, then the overall algorithm takes $O(f(N) + g(N))$ steps. Of course, that's fairly obvious. What's more interesting is to remember that you can then simplify $O(f(N) + g(N))$ to either $O(f(N))$ or $O(g(N))$, depending which function grows faster.

Hidden loops

Don't forget that sometimes code can have "hidden" loops. How long would the following code take to determine whether a given number appears in an $M \times N$ matrix? 

#include <vector>
#include <algorithm>
bool matrixContains(int target, std::vector<std::vector<int>> mat) {
    // Assume mat is as an M x N matrix
    const int M = mat.size();
    for (int i = 0; i < M; ++i) {
        if (std::find(mat[i].begin(), mat[i].end(), target) != mat[i].end())
            return true;
    }
    return false;
}

It takes $O(MN)$ time to search the matrix. While the code may look like a single loop, it's actually a nested loop in disguise: for each i, std::find runs a loop that loops through each element in mat[i] to look for target. Since we have assumed that each row has $N$ elements, this takes $O(N)$ time. We need to call std::find $M$ times, so the total time required is $O(MN)$. Of course, this is unsurprising: the matrix has $MN$ elements, so of course checking them all takes $O(MN)$ time.

Note that this is our first example using big-$O$ notation with two independent variables. It means exactly what you expect, that there exists a constant $C$ such that the number of steps required is $\leq CMN$ for all large $M, N$.

This is also a good example of the general rule that when you have nested loops, the iteration counts multiply. If the outer loop runs through $M$ iterations and the inner loop runs through $N$ iterations, then the whole process requires $MN$ iterations.

Examples of other algorithms

Best time to buy/sell

Suppose we're given a std::vector<double> containing $N$ prices of a stock, and we want to determine what were the best time to buy and sell that stock, assuming you could only buy once. How long does it take to solve that problem?

Answer: It depends on the algorithm you use, but the best solution is $O(N)$. The naive solution would be to use a double loop to run through all possible pairs of times to buy and sell. There are $N(N-1)/2$ such pairs, which is $O(N^2)$. But there's a better algorithm, which allows us to find the answer while only looping through the list once. Start by guessing that you're going to buy at time 0. Loop through the list, looking at each subsequent time $t$ and seeing how much profit you would make by selling then. However, if the price at time $t$ is lower than the price at time 0, then it no longer makes sense to compare subsequent times with time 0; you make more profit by buying at time $t$ and selling at time $t+k$ than be buying at time 0. Instead, use time $t$ as your new "time 0" and proceed from there. This requires only one loop through the list, so it is $O(N)$.

This is a good illustration of how choosing your algorithm wisely can meaningfully change the time complexity of a given problem. A wise choice of algorithm can make the difference in whether a problem is practically solvable or not.

Generate all subsets

Suppose that I give you a set of $N$ numbers, and I ask you to generate all the subsets of that set. If you choose a sensible algorithm to generate them, then each subset can be generated relatively quickly, so the only real issue is the sheer number of subsets. In other words, the time required will be $O(\text{number of subsets})$. The number of subsets is $2^N$ because when we form a subset, for each of the $N$ numbers, we have two choices: include it or exclude it. Therefore generating all the subsets takes time $O(2^N)$. This grows extremely quickly, so any algorithm that involves generating all the subsets will not be practical unless $N$ is extremely small. If you encountered a problem that asks something about all subsets, you would probably need to come up with a more clever algorithm than brute force.

Generate all permutations

Suppose I give you a string of $N$ distinct characters, and I ask you to print all the permutations (rearrangements) of those characters. Similar to the previous example, this will be $O(\text{number of permutations})$. The number of permutations is $N!$ because there are $N$ choices for the first character, times $N-1$ choices for the second, times $N-2$ choices for the third, and so on. Thus, generating permutations is $O(N!)$. This grows even faster than $O(2^N)$, so you definitely would not want to use a $O(N!)$ algorithm unless $N$ was very small.

Search an unsorted vector

We mentioned above that std::find (indeed, any algorithm to search an unsorted vector of size $N$) will take time $O(N)$, because there's nothing to do but check all $N$ entries.

Search a sorted vector

If the vector is already sorted, then there's a faster algorithm to search it, called binary search. The idea is that we check the midpoint of the vector. If the value there is target, then we're done. Otherwise, because the vector is sorted, we need only check the remaining left/right half of the vector depending whether the value at the midpoint was greater/less than target. Thus, we've cut the problem in half with a single check! Now we can repeat the process with the leftover half: check its midpoint, and (if necessary) cut it in half again. Thus after 2 checks we're down to 1/4 the size of the original vector, after 3 checks we're down to 1/8 the original size, and after $k$ checks we're down to $1/2^k$ of the original size. Therefore we'll have the search narrowed down to a single element once $2^k \approx N$, i.e., $k \approx \log_2 N$. This proves that binary search takes time $O(\log N)$ to search a sorted vector. (Note that when we write a logarithm in big-$O$ notation, we don't need to specify the base, because all algorithms $\log_b$ with $b>1$ are constant multiples of each other thankes to the change-of-base formula.)

Here's the code for a binary search algorithm: 

#include <vector>

// Search a sorted vector v for target. 
// Return the index of target if found, otherwise return -1
int binarySearch(int target, const std::vector<int>& v) {
    int lo = 0, hi = v.size() - 1;

    while (lo <= hi) {
        int m = lo + (hi - lo) / 2; // Calculate midpoint without overflow
        if (v[m] == target)     {return m;}
        else if (v[m] < target) {lo = m + 1;}
        else                    {hi = m - 1;}
    }
    return -1;
}

You should know how to code binary search yourself -- it's a classic test question for this type of course. But when you're writing code, you'll almost never write your own binary search, because the standard library already contains binary search functions in the algorithm header. Specifically, there's std::binary_search which returns a boolean telling you whether the target is in the vector. There's also std::lower_bound, which returns an iterator to the first element that is greater than or equal to the target. This is the one that you'll use if you want to find the actual index of the target (whether you need to know the index where it actually appears, or the index where it would appear if it were inserted in the appropriate, sorted place).

Above, we gave an explanation for why binary search takes $O(\log N)$ time. But we needed to do a little bit of math to solve that. In this case, we were lucky that the math wasn't too complicated, but we would like to have a shortcut for similar problems. Before we do that, we'll discuss some more background material first.

Different types of time complexity analysis

So far, we've largely been interested in analyzing the worst-case time complexity of algorithms. For example, if you're searching an unsorted vector for a given value, the worst-case number of checks is $N$, if the value isn't in the vector, so we say that the worst-case time complexity is $O(N)$. Of course, the best-case scenario is that the target value is the first entry in the vector and we find it immediately, so the best-case time complexity is $O(1)$.

Naturally, it is very rare to care about the best-case time complexity. Somebody waiting for their computer to solve a problem won't feel better if you tell them that the computer would have solved it quickly if the data had been in one specific, best-case form. However, that doesn't mean that we only care about the worst-case either. In many situations, we might care more about the average complexity: we can accept that an algorithm will occasionally be slow, if it's balanced out by other situations where it's fast. (On the other hand, that's not always the case. For performance-critical software that needs to respond quickly in an emergency, we need to know that it will react in time every time, not just on average.)

There are two subtly-different types of average complexity that we consider:

Average-case time complexity measures the expected running time of an operation when averaged across all possible sets of input data. For example, if we want to find the index of a value in an unsorted vector (and we know that the value is present), then on average we'll need to search half the vector before we find the target, so the average complexity is $N/2$. In big-$O$ notation, this is still $O(N)$, same as we got for the worst-case analysis.

Amortized time complexity measures the worst-case average cost per operation over a sequence of multiple operations. Note that this is different from average-case time complexity because it only considers sequences of operations that could actually occur, not randomly-chosen operations, and it provides a guarantee that the total cost in the long term will never be worse than the amortized time complexity. (With average-case time complexity, on the other hand, there's no such guarantee. You could get unlucky and have all your inputs be the "bad" cases.)

An excellent example of amortized time complexity is std::vector::push_back. Remember that std::vector stores its data in contiguous memory, like a C-style array. If the allocated memory had just enough memory to store the current data, then every time you tried to add a new entry to the vector, the program would need to more to a new, larger block of memory and copy all the data over to the new memory location. Naturally, this takes $O(N)$ time. But we want push_back to be efficient, so this is undesirable. Instead, the compiler allocates some extra, empty memory at the end of the vector, so that there's space to insert new elements at the end without needing to copy all the data. This makes push_back very fast: you simply copy the new data into the memory that's already sitting at the end of the vector waiting for your data, a $O(1)$ operation. But if you insert enough new elements, eventually you'll run out of space anyway, triggering the expensive $O(N)$ copy operation.

Thus, the worst-case time complexity of push_back must unavoidably by $O(N)$, because eventually we'll run out of memory and trigger the $O(N)$ copy. But, it would be nice if std::vector were designed so that the amortized time complexity is better than $O(N)$. If std::vector sets aside enough empty memory when it's allocated that it won't need to do the $O(N)$ copy too often, then the rare, expensive copy can be averaged with the usual cheap $O(1)$ insertion to make push_back fast on average.

So, if we were the designers of std::vector and we were allocating memory for a vector that currently holds $N$ entries, how much extra memory should we include at the end? If we tried to include memory for two extra entries, that wouldn't be good enough: the next two calls to push_back would take $O(1)$ time, but the third would take $O(N)$ time, for an average of $O((1+1+N)/3) = O(N)$. That's what we were trying to avoid.

Instead, we need to include a lot of extra memory, so that the worst-case scenario happens much more rarely. But we also don't want to take too much memory: if std::vector constantly claimed a lot of memory just to sit empty in case of insertions, we might risk running out of memory while a lot of memory sat empty. Thus, we have a tradeoff: we need to allocate enough memory to amortize the cost of push_back, without taking dramatically more than is needed to fulfill that goal.

It turns out that we can solve this problem with a fairly simple answer: when we allocate a new block of memory for a vector that currently has $N$ entries, we take enough memory for $2N$ entries. (In the real world, some implementations may use a number other than 2, e.g., 1.5. But 2 makes the math easy.) When we leave $N$ empty memory slots, we guarantee that the next $N$ insertions will be $O(1)$, and then the next after that will be $O(N)$. This gives us an amortized time complexity of

\[O((1+1+\dotsb+1+1+N)/(N+1)) = O((2N+1)/(N+1)) = O(1).\]

Therefore, the amortized time complexity of push_back is $O(1)$. On average, each call to push_back takes constant time, even though there are occasional slow calls.

Other asymptotic notations

So far, big-$O$ notation has been perfect for our purposes. Saying that $f(N) = O(g(N))$ says that $\lvert f(N) \rvert \leq Cg(N)$, so we can use big-$O$ notation without worrying too much about the fact that our algorithms might have a best-case performance substantially better than $Cg(N)$. But it would also be nice to have a more-specific notation. For example, if $f(N) = O(N^2)$, then it's also true that $f(N) = O(N^3)$, but we wouldn't want to write the latter because it loses valuable information. Generally when we say that the time complexity of an algorithm is $O(N^3)$, that implies that the time complexity is not $O(N^2)$, or else we would have written that; nonetheless, it would be nice to have a notation that explicitly promises this.

The big-$\Theta$ notation does that for us. If we write $f(N) = \Theta(g(N))$, that means that there exist constants $c, C > 0$ such that $cg(N) \leq \lvert f(N) \rvert \leq Cg(N)$. Thus, $g(N)$ is a tight bound. In algorithmic terms the algorithm takes exactly $g(N)$ steps, up to a constant factor.

We'll usually use big-$O$ notation since, as we saw above, it captures the worst-case behavior that we generally care most about. But sometimes it's nice to have notation that states succinctly that a given bound is optimal.

One last piece of notation that we'll need to state the following theorem is big-$\Omega$ notation. This is the opposite of big-$O$ notation; where big-$O$ notation gives an upper bound, big-$\Omega$ notation gives a lower bound. (I.e., it says "the algorithm takes at least this much time.") Formally, $f(N) = \Omega(g(N))$ means that there exists some $C>0$ such that $f(N) > Cg(N)$ for all sufficiently large $N$.

Of course, big-$\Theta$ notation will generally not be our final answer in evaluating an algorithm: we usually want to know how fast an algorithm is, not how fast it isn't. But it can be useful to know when an algorithm isn't fast (if only so we can avoid it).

The Master Theorem

We saw above that we could calculate the time-complexity of binary search by observing that it repeatedly cuts the search space into two halves, and then asks us to look at one of those halves. More generally, there are a lot of algorithms that cut a problem of size $N$ into $a$ subproblems of size $N/b$. If $T(N)$ is the number of steps required to solve the problem, then it takes $aT(N/b)$ steps to solve all these subproblems. After that, it may take an additional $f(N)$ steps to recombine the answers to the subproblems into an answer to the original problem. Thus, we have $T(N) = aT(N/b) + f(N)$. The master theorem tells us how to determine the time complexity of such an algorithm.

Theorem: Let $a \geq 1$ and $b>1$ be constants, let $f(N)$ be a function, and let $T(N)$ be defined on the nonnegative integers by the recurrence $T(N) = aT(N/b) + f(N)$. (We interpret $T(N/b)$ by rounding $N/b$ up or down to an integer.) Then:

  • If $f(N) = O(N^{\log_b a - \epsilon})$ for some $\epsilon > 0$, then $T(N) = \Theta(N^{\log_b a})$.
  • If $f(N) = \Theta(N^{\log_b a})$, then $T(N) = \Theta(N^{\log_b a} \log N)$.
  • If $f(N) = \Omega(N^{\log_b a + \epsilon})$ for some $\epsilon > 0$, and there exists a constant $c<1$ such that $af(N/b) \leq cf(N)$ for all sufficiently large $N$, then $T(N) = \Theta(f(N))$.

(In practice, you can usually ignore the regularity condition $af(N/b) \leq cf(N)$ in the third case; it will almost always be satisfied for any $f$ arising in practice.)

To understand the idea behind this theorem, start by ignoring the $f(N)$. If it were free to recombine our subproblems, we would have simply $T(N) = aT(N/b)$, which is satisfied by $T(N) = CN^{\log_b a}$. If $f$ is small, then we will still have $T(N) \approx CN^{\log_b a}$, which is the first case in the theorem.

On the other hand, if the cost to recombine the subproblems is meaningfully large, that may show up in our final answer. If $f$ is comparable to our "expected" $T$, then taking $f$ into account doesn't make $T$ too much bigger: the second case only costs an extra factor of $\log N$ compared to the first case. On the other hand, if $f$ costs even more than solving the subproblems, then the cost of the algorithm is dominated by $f$.

Examples of the Master Theorem

We saw above that for binary search, $T(N) = T(N/2) + \Theta(1)$. Thus $a=1$ and $b=2$, so the critical exponent is $\log_2 1 = 0$. In this case, $f(N) = O(N^0)$, so we're in the second case, which tells us that $T(N) = \Theta(N^0 \log N) = \Theta(\log N)$, as we saw above.

You may be familiar with merge sort, a sorting algorithm that works by splitting the list in half, sorting each half, and then merging them back together. This gives us the recurrence $T(N) = 2T(N/2) + \Theta(N)$, which leads to the critical exponent $\log_2 2 = 1$. Thus we are again in the second case, which proves that merge sort is $\Theta(N \log N)$.

Lecture 11: Inheritance

Before we get to the main lecture on inheritance, there are a couple more C++ keywords that are worth discussing.

static and constexpr

As you may already know from Python, sometimes we have attributes/methods that we want to assign to a class as a whole, rather than having a separate value for each instance of the class. These are called static members.

For example, a CustomerAccount class might keep track of how much money a customer owes your business, and the business might charge a late fee to clients who haven't paid by a certain date. Assume that every customer is charged an extra 10% for any fees that are unpaid by the end of the month. Since the 10% is the same for every account, it makes sense that it should be defined once for the entire class, rather than being an attribute of each instance, so it's conceptually clearer for it to be declared as a static variable. There's also a practical reason why it must be static; if you declare a non-static attribute as a constant, then the compiler won't define a default operator= for you. (The default behavior would be to reassign each member variable, which it can't do if one of the member variables is declared as const.) Therefore, if we try to declare the late fee as a non-static constant, the below code doesn't compile: 

class CustomerAccount {
public:
    double balance = 0;
    void charge(double amt) {balance += amt;}
    void receivePayment(double amt) {balance -= amt;}
    void applyLateFee() {if (balance > 0) balance *= 1 + LateFee;}
private:
    const double LateFee{0.10};
};

int main() {
    CustomerAccount acct1, acct2;
    acct2 = acct1; // operator= is undefined!
}

Declaring LateFee as static solves this problem, but then it creates another problem: 

class CustomerAccount {
public:
    double balance = 0;
    void charge(double amt) {balance += amt;}
    void receivePayment(double amt) {balance -= amt;}
    void applyLateFee() {if (balance > 0) balance *= 1 + LateFee;}
private:
    static const double LateFee{0.10};
};

C++ doesn't allow you to initialize non-integral types as static const inside a class. One solution is to move the initialization outside the class: write static const double LateFee; inside the class, and const double CustomerAccount::LateFee = 0.10; outside the class. But this is inelegant. C++11 introduced a better solution: use constexpr instead of const. Declaring a variable as constexpr means not only that it's constant, but that its value can be determined at compile time. C++ allows non-integral types to be static constexpr, so the below code works: 

class CustomerAccount {
public:
    double balance = 0;
    void charge(double amt) {balance += amt;}
    void receivePayment(double amt) {balance -= amt;}
    void applyLateFee() {if (balance > 0) balance *= 1 + LateFee;}
private:
    static constexpr double LateFee{0.10};
};

Inheritance

You should already be familiar with the basic idea of inheritance from Python: inheritance represents the "is a" relationship between classes. That is, the derived class is a specific type of the base class. One of the classic examples: suppose you have an Animal class and a Dog class. The Dog class could inherit from the Animal class, because a dog is a type of animal.

One benefit of inheritance is that it avoids code reuse. If you have behaviors that are common to every animal, they can be defined in the Animal class, and then the Dog class automatically inherits those behaviors, so that you don't need to rewrite all of that code in the Dog class.

Another benefit is polymorphism: if you have a function that accepts an Animal as its argument, then it can also accept a Dog, Cat, Bird, etc.

Example: Employee

Consider the following class, which represents a salaried employee at a company that pays its employees weekly: 

#include <string>

class SalariedEmployee {
public:
    Employee(std::string name, double salary) : 
        name_(name), weeklySalary_(salary) {}
    double getThisWeeksPay() const {return weeklySalary_;}
    void pay() const {std::cout << "Paid $" << getThisWeeksPay() << " to " << name_ << std::endl;}
    void endWeek() {pay();}
    void raise(double r) {weeklySalary_ += r;}
private:
    std::string name_;
    double weeklySalary_;
};

This is fairly reasonable for a generic class representing any salaried employee. The one thing that might confuse you is why we have separate pay() and endWeek() methods, when endWeek() simply invokes pay() anyway. Right now, the only thing that we need to do for employees at the end of the week is pay them, but you could imagine that in the future we might have multiple weekly tasks we need to perform for each employee. Our code will be easier to maintain if we plan ahead for that future now, by recognizing that the function we call at the end of the week won't always just be the pay() function, and making it a separate function to start.

Next, we might have other needs for specific types of employees. For example, we might want a class for salespeople which tracks their sales: 

class SalesEmployee : public SalariedEmployee {
public:
    SalesEmployee(std::string name, double salary) : SalariedEmployee(name, salary) {}
    void makeSale(double amt) {weeklySales_ += amt;}
    double weeklySales() const {return weeklySales_;}
    void endWeek() {pay(); weeklySales_ = 0;}
private:
    double weeklySales_{0};
};

This is a very basic example of inheritance. Notice how it works:

  • The code class SalesEmployee : public SalariedEmployee says that SalesEmployee inherits from SalariedEmployee. The use of public means that anything that was a public attribute/method of the base class will continue to be public in the derived class. (Similarly, anything that was private will continue to be private. Anything that was protected -- which we'll discuss soon -- will continue to be protected.)
  • Note that we can define a constructor for SalesEmployee easily, by callng a constructor of SalariedEmployee. In this case, we didn't need to include initialize weeklySales_ explicitly in the constructor, because it already has a default value of 0. But if we needed to explicitly initialize any attributes of the base class, we could have done that after the base class initializer, using the usual member initializer list syntax. (As usual, if we wanted our SalesEmployee constructor to do more after the member initializers finished, we could also have put more code inside the braces where we currently have an empty function body.)
  • Of course, we were able to add additional attributes/methods that the base class lacked; in this case, we added the ability to track sales. That's the point of inheritance: a derived class inherits the behavior of its base class, but also has appropriate behavior specific to its type.
  • We were also able to override the endWeek() method, because there are two things that need to happen to a SalesEmployee at the end of a week: they need to get paid, and their weekly sales need to be reset to 0. This is a very valuable ability: the fact that we can override methods of the base class means that we can take advantage of inheritance even when the methods of the base class aren't 100% what we want in the derived class. (Technically, we didn't override the method -- we hid it by creating another function with the same name. We'll see a little bit later what the distinction between the two concepts is, and how hiding when you mean to override can lead to subtle bugs. But before we can talk about that, we'll need to talk about some other stuff first.)

If you want, you can check that the below code prints what you expect. In particular, note that the last line says that Bob's weekly sales are 0, because the compiler correctly used the endWeek() method for SalesEmployee (which resets the weekly sales), rather than the endWeek() method for SalariedEmployee. 

#include <iostream>
#include <string>

class SalariedEmployee {
public:
    SalariedEmployee(std::string name, double salary) : 
        name_(name), weeklySalary_(salary) {}
    double getThisWeeksPay() const {return weeklySalary_;}
    void pay() const {std::cout << "Paid $" << getThisWeeksPay() << " to " << name_ << std::endl;}
    void endWeek() {pay();}
    void raise(double r) {weeklySalary_ += r;}
private:
    std::string name_;
    double weeklySalary_;
};

class SalesEmployee : public SalariedEmployee {
public:
    SalesEmployee(std::string name, double salary) : SalariedEmployee(name, salary) {}
    void makeSale(double amt) {weeklySales_ += amt;}
    double weeklySales() const {return weeklySales_;}
    void endWeek() {pay(); weeklySales_ = 0;}
private:
    double weeklySales_{0};
};

int main() {
    SalesEmployee bob("Bob", 1500);
    bob.endWeek();                                                  // Paid $1500 to Bob
    std::cout << "Bob's sales: " << bob.weeklySales() << std::endl; // Bob's sales: 0
    bob.makeSale(10000); 
    std::cout << "Bob's sales: " << bob.weeklySales() << std::endl; // Bob's sales: 10000
    bob.raise(200);
    bob.endWeek();                                                  // Paid $1700 to Bob
    std::cout << "Bob's sales: " << bob.weeklySales() << std::endl; // Bob's sales: 0
}

But what if that's not how we want the SalesEmployee class to behave? For example, maybe salespeople get paid a commission (a percentage of their sales)? In that case, we will also need to override the behavior of getThisWeeksPay(): 

class SalesEmployee : public SalariedEmployee {
public:
    SalesEmployee(std::string name, double salary) : SalariedEmployee(name, salary) {}
    void makeSale(double amt) {weeklySales_ += amt;}
    double weeklySales() const {return weeklySales_;}
    void endWeek() {pay(); weeklySales_ = 0;}
    double getThisWeeksPay() const {return weeklySalary_ + commission_ * weeklySales_;}
private:
    static constexpr double commission_{0.10};
    double weeklySales_{0};
};

If you try to replace the previous definition of SalesEmployee with this one, the code won't compile. The problem is that weeklySalary_ is a private member of SalariedEmployee, which means that it can't be accessed outside of SalariedEmployee. You might have expected that SalesEmployee could access private members of SalariedEmployee, since it inherits from SalariedEmployee, but that's not how C++ works. If you want members of the base class to be accessible to derived classes while still being inaccessible to the outside world, you need something else:

protected

The level between public and private is protected: it means that the attribute is accessible to derived classes, but otherwise inaccessible outside the class. That's exactly what we need to solve the problem we had above. Edit the above code so that weeklySalary_ is protected instead of private: 

#include <iostream>
#include <string>

class SalariedEmployee {
public:
    SalariedEmployee(std::string name, double salary) : 
        name_(name), weeklySalary_(salary) {}
    double getThisWeeksPay() const {return weeklySalary_;}
    void pay() const {std::cout << "Paid $" << getThisWeeksPay() << " to " << name_ << std::endl;}
    void endWeek() {pay();}
    void raise(double r) {weeklySalary_ += r;}
private:
    std::string name_;
protected:
    double weeklySalary_;
};

class SalesEmployee : public SalariedEmployee {
public:
    SalesEmployee(std::string name, double salary) : SalariedEmployee(name, salary) {}
    void makeSale(double amt) {weeklySales_ += amt;}
    double weeklySales() const {return weeklySales_;}
    void endWeek() {pay(); weeklySales_ = 0;}
    double getThisWeeksPay() const {return weeklySalary_ + commission_ * weeklySales_;}
private:
    static constexpr double commission_{0.10};
    double weeklySales_{0};
};

int main() {
    SalesEmployee bob("Bob", 1500);
    bob.makeSale(10000);
    std::cout << bob.getThisWeeksPay() << std::endl; // 2500                (correct)
    bob.endWeek();                                   // Paid $1500 to Bob   (oops)
}

This compiles, and it might even look right, but if you run the code, it will pay Bob $1500 rather than the $2500 he's owed.

When we call bob.getThisWeeksPay(), it correctly returns 2500, but then the endWeek() method pays Bob the wrong amount anyway! The problem is that endWeek() calls the pay() method from SalariedEmployee, which in turn calls the getThisWeeksPay(). But since pay() comes from SalariedEmployee, the getThisWeeksPay() that it calls is the SalariedEmployee version, even though we intended for that version to be overridden.

A similar issue arises if we try to use a SalariedEmployee* to point to a SalesEmployee object. This is legal, because a SalesEmployee is a type of SalariedEmployee. But when we do that, the compiler decides which version of getThisWeeksPay() to use for ptr->getThisWeeksPay() based on the type of the pointer, so it uses the SalariedEmployee version, which isn't what we want. 

int main() {
    SalesEmployee bob("Bob", 1500);
    bob.makeSale(10000);
    SalariedEmployee* ptr = &bob;
    std::cout << ptr->getThisWeeksPay() << std::endl; // Prints 1500 rather than 2500
}

You might feel that this example is a little artificial -- why did we use a SalariedEmployee* to point to something that we know is a SalesEmployee? The below is another version of the same issue, which might feel more natural: what if we want to put all the employees into a single vector? When we loop over that vector, the loop variable employee must be a SalariedEmployee, so employee.endWeek() will always call the SalariedEmployee version. Not only does the system pay Bob the wrong amount, but it also fails to reset his weekly sales at the end of the week. 

int main() {
    SalariedEmployee alice("Alice", 2000);
    SalesEmployee bob("Bob", 1500);
    bob.makeSale(10000);
    std::vector<SalariedEmployee> employees = {alice, bob};
    for (auto employee : employees) {
        employee.endWeek();
    }
    std::cout << bob.weeklySales() << std::endl; // Prints 10000
}

This is the subtlety I mentioned earlier, about how we were actually hiding methods rather than overriding them. With hidden methods, the compiler chooses at compile time which method to use based on the declared type of the object, rather than choosing at runtime based on the actual type. If you want to override instead (which you usually will), you will need:

virtual

When declaring a method that you intend to override later, you should declare it as virtual. Declaring a method as virtual tells the compiler that it should resolve the function call at runtime based on the actual type of the object, rather than basing it on the declared type. This solves the problem that we had above: if we have a SalesEmployee object and we attempt to call its endWeek() method, we will always get SalesEmployee::endWeek(), regardless of whether the variable that we used to access the object was a SalesEmployee, SalariedEmployee*, or SalariedEmployee.

You can run the below code and check that it works correctly now. If you want, you can also experiment with the other situations that were a problem before we started using virtual, and check that they also work correctly. 

#include <iostream>
#include <string>

class SalariedEmployee {
public:
    SalariedEmployee(std::string name, double salary) : 
        name_(name), weeklySalary_(salary) {}
    virtual double getThisWeeksPay() const {return weeklySalary_;}
    void pay() const {std::cout << "Paid $" << getThisWeeksPay() << " to " << name_ << std::endl;}
    virtual void endWeek() {pay();}
    void raise(double r) {weeklySalary_ += r;}
private:
    std::string name_;
protected:
    double weeklySalary_;
};

class SalesEmployee : public SalariedEmployee {
public:
    SalesEmployee(std::string name, double salary) : SalariedEmployee(name, salary) {}
    void makeSale(double amt) {weeklySales_ += amt;}
    double weeklySales() const {return weeklySales_;}
    void endWeek() {pay(); weeklySales_ = 0;}
    double getThisWeeksPay() const {return weeklySalary_ + commission_ * weeklySales_;}
private:
    static constexpr double commission_{0.10};
    double weeklySales_{0};
};

int main() {
    SalesEmployee bob("Bob", 1500);
    bob.makeSale(10000); 
    bob.endWeek();                                                  // Paid $2500 to Bob
    std::cout << "Bob's sales: " << bob.weeklySales() << std::endl; // Bob's sales: 0
}

override

The override keyword tells the compiler that the method you're declaring is supposed to override a virtual method. As we saw above, it's not strictly necessary -- the override will still happen even with the keyword. But it is considered best practice. It you make a typo in the overriding method, so that it's declared slightly differently and it doesn't actually override the original, having the override keyword in place helps you catch the bug. The compiler will refuse to compile the code if something that's supposed to be an override isn't actually overriding anything.

Thus, we should replace the declarations of endWeek() and getThisWeeksPay() in SalesEmployee with the following: 

void endWeek() override {pay(); weeklySales_ = 0;}
double getThisWeeksPay() const override {return weeklySalary_ + commission_ * weeklySales_;}

Virtual destructors

We've just seen that methods that might be overridden should be declared as virtual. A subtle point worth noting is that this applies to destructors too. Suppose you wrote code like this: 

Base* b = new Derived;
delete b;

If the destructor for Base wasn't declared as virtual, then this will call that destructor, rather than the Derived destructor. This leads to undefined behavior.

Therefore, if there's any chance of this situation arising (where a derived class is referenced polymorphically by a base pointer), you should declare the destructor of the base class as virtual. This shouldn't be too much trouble, because you can simply declare it as default.

This triggers other Rule of Five issues. When you define a destructor explicitly (even if you do so using default), the compiler no longer automatically generated move methods, so if you want those, you need to redefine them yourself (which again, you could do using default). But the copy operators can also lead to annoying issues -- if you copy an object of a derived class into a variable of the base class, that loses information (this is called slicing) and may lead to undesired behavior. For that reason, it's sometimes suggested that, when using polymorphism, you delete the other four Rule of Five methods. You can do that using delete, just like you would use default.

Again, you can skip all of this if you're certain that your derived class will never be accessed via a base pointer. In this course, you can usually skip it. I won't penalize you for skipping a virtual destructor unless it's actually necessary to make existing code work correctly.

Pure Virtual Functions and Abstract Classes

What if our company also has employees that are paid hourly wages? We could create a new class Employee, and have SalariedEmployee and WageEmployee both inherit from that. The code might look something like this: 

#include <iostream>
#include <string>

class Employee {
public:
    Employee(std::string name) : name_(name) {}
    virtual ~Employee() = default;
    virtual double getThisWeeksPay() const = 0;
    void pay() const {std::cout << "Paid $" << getThisWeeksPay() << " to " << name_ << std::endl;}
    virtual void endWeek() {pay();}
    virtual void raise(double r) = 0;
private:
    std::string name_;
};

class WageEmployee : public Employee {
public:
    WageEmployee(std::string name, double wage) : 
        Employee(name), hourlyWage_(wage) {}
    void work(double hours) {hoursWorked_ += hours;}
    double getThisWeeksPay() const override {return hoursWorked_ * hourlyWage_;}
    void endWeek() override {pay(); hoursWorked_ = 0;}
    void raise(double r) override {hourlyWage_ += r;}
private:
    double hoursWorked_{0};
    double hourlyWage_;
};

class SalariedEmployee : public Employee {
public:
    SalariedEmployee(std::string name, double salary) : 
        Employee(name), weeklySalary_(salary) {}
    virtual ~SalariedEmployee() = default;
    virtual double getThisWeeksPay() const override {return weeklySalary_;}
    void raise(double r) override {weeklySalary_ += r;}
protected:
    double weeklySalary_;
};

class SalesEmployee : public SalariedEmployee {
public:
    SalesEmployee(std::string name, double salary) : SalariedEmployee(name, salary) {}
    void makeSale(double amt) {weeklySales_ += amt;}
    double weeklySales() const {return weeklySales_;}
    void endWeek() override {pay(); weeklySales_ = 0;}
    double getThisWeeksPay() const override {return weeklySalary_ + commission_ * weeklySales_;}
private:
    static constexpr double commission_{0.10};
    double weeklySales_{0};
};

This code introduces a few new concepts that we haven't discussed before:

  • Now, SalesEmployee inherits from SalariedEmployee, which inherits from Employee. This means that transitively, SalesEmployee inherits from Employee as well. (This should make intuitive sense. Inheritance represents an "is a" relationship: if every A is a B and every B is a C, then certainly every A is a C.) We can write code like Employee* p = new SalesEmployee("Bob", 1500); and it will compile.
  • Notice the declaration virtual double getThisWeeksPay() const = 0;. The "= 0" means that this is a pure virtual function; it has no definition. Therefore, derived classes must provide their own implementation.
  • Since Employee has a pure virtual function, it is an abstract class. An abstract class cannot be instatiated directly, since that would create an instance with an undefined method. It can only be instantiated indirectly, by instantiating a derived class which implements all the pure virtual methods.
